==================== 三、实现要点 ====================

1) 工装 2 检索快照（build_retrieval_snapshot）
   - 条目数、各条 score、**实际进入 prompt 的条目**（按条目正文是否出现在注入文本判定）、
     注入文本 token（injected_tokens）；
   - 条目取值口径与 PromptAssembler（content/text/chunk/name + results/documents/memories/items）
     保持一致，避免两处口径漂移。

2) 工装 4 归因 A（attribution_a + extract_key_terms）
   - 词项抽取：ASCII 词（≥3 字符）+ 相邻词二元组；CJK 连续段二元组；
   - 判定规则：**any-hit**（片段任一词项出现在回答即视为被使用）；零额外模型调用；
   - 保守规则已在模块内文档声明：**只能纵向对比，不得作绝对值解读**（与派单 §5.3 一致）；
   - 命中词项逐片段可追溯（matched_terms），供报告核查。

3) 工装 3 回执（ContextReceipt / build_receipt / build_receipt_from_result）
   - 汇总入口 build_receipt_from_result：一次调用完成「检索快照 → 片段切分（按注入上下文逐行）
     → 归因 A → 回执」，可被网关直接调用；
   - 回执字段：维度（request_id / session_id / model / created_at）+ 工装 1（prompt_total_tokens /
     六段分项 / contexts_tokens）+ 工装 2（memory / rag 快照）+ 工装 4（used / unused /
     used_ratio / matched_terms）；to_json() 便于批量导出。

4) 落库通道（已核实）
   - 网关同步路径：routing_trace["context_metrics"] = 回执记录；
   - _save_trace（openllm_gateway.py:1412）执行
     `trace_record.set_metadata({"mode","pipeline","routing_trace"})` + `db.commit()`
     → **回执随 routing_trace 落库**；
   - 查询通道：`/openllm/v1/trace/{request_id}`（既有接口）可读取该 metadata。

5) 红线（AC-148-01-5）
   - 回执只落计量数值、判定标记与命中的**短词项**；不落 Prompt 全文、不落回答全文、
     不落令牌/密码/密钥；单元用例显式断言。
