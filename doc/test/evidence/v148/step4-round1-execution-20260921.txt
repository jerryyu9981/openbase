-- 步骤 2：标准启动入口的阻断（环境缺陷，已定位） --
入口：backend/run_backend.py（模块 docstring：本地开发后端启动入口（含 .pylib 依赖））
该入口执行 sys.path.insert(0, os.path.join(BACKEND_DIR, ".pylib"))，把 backend/.pylib 置于 path 最前。
实测：以 run_backend.py 启动 → 在导入 main:app 阶段连续两次 ImportError：
  ① cryptography.hazmat.bindings._rust → DLL load failed while importing _rust: 找不到指定的程序
  ② grpc._cython.cygrpc               → cannot import name 'cygrpc' from 'grpc._cython'
根因判定：backend/.pylib 为**多版本混杂的损坏目录**——同一目录并存
  cryptography-49.0.0 与 cryptography-50.0.0 两份 dist-info、cffi 2.1.0/2.1.1、
  greenlet 3.5.4/3.5.5、idna 3.18/3.19、uvicorn 0.52.0/0.52.4、rpds_py 两份 等，
  其原生扩展在本机 Python 3.10.11 下无法加载。
对照实验：同解释器下 .pylib 置于 path 最前 → 复现 ImportError；
  不使用 .pylib（仅 backend 目录 + 系统 site-packages）→ 导入成功，cryptography 46.0.7 rust 绑定可用。
定性：该缺陷与 v1.4.8 改动**无关**（本版本未触碰 run_backend.py 与 .pylib），属既有环境问题；
  测试侧 tests/unit/conftest.py 存在**同类** path 前置问题并已在本版本修复（见 DevLogReport §13），
  两者同源 → 登记为环境类缺陷，待处置。

==================== 十五、回写链路「跨系统鉴权前置」根因定位（只读排查，未改任何代码） ====================

-- 现象（§十三 步骤 4 根因 A 的追查） --
`POST /openllm/v1/writeback`（target=memory, mode=sync）→ 500；
服务端 WARNING：`同步回写失败: target=memory err=组件 open_memory 不可用:
  HTTP 401: 缺少 Bearer Token，请在 Authorization 请求头中提供 JWT (status=401)`；
出站证据：`httpx` INFO `POST http://127.0.0.1:8020/api/v1/remember "HTTP/1.1 401 Unauthorized"`。

-- 排查步骤 1：OpenMemory 网关鉴权顺序（`src/openmemory/gateway/gateway.py`） --
· 白名单 `_WHITELIST` = {`/health`, `/health/readiness`, `/health/liveness`, `/api/v1/health`,
  `/metrics`, `/docs`, `/openapi.json`} → **`/api/v1/remember` 不在白名单**；
· 鉴权为**顺序两段**：先 `if self._config.api_key:` 校验 `X-API-Key`（CR-010：未配置则不强制），
  **再** `if self._enable_jwt:` 校验 `Authorization: Bearer`（缺 token 即 401「缺少 Bearer Token」）；
· `_enable_jwt = bool(config.jwt_secret) or config.oidc_mode == "gateway"`（`gateway.py:62`）。
· **判定**：两段是**并且**关系而非二选一 → **即使 `X-API-Key` 正确，只要 `_enable_jwt` 为真，缺 Bearer 仍 401**。
  实测报的是 JWT 错误（而非「缺少或无效的 API Key」）→ 说明 **JWT 分支被启用**。

-- 排查步骤 2：运行实例（8020）的配置来源 --
`src/openmemory/server.py:592` `gw_config = GatewayConfig(api_key=config.server.api_key or "",
  jwt_secret=config.gateway.jwt_secret or "", oidc_mode=config.gateway.oidc_mode, ...)`；
OpenMemory `.env` 实际声明（仅列键名）：`OPENMEMORY_SERVER__API_KEY`、`OPENMEMORY_GATEWAY__ENABLED`、
**`OPENMEMORY_GATEWAY__JWT_SECRET`**、`OPENMEMORY_GATEWAY__JWT_ALGORITHM`、`OPENMEMORY_GATEWAY__OIDC_MODE`；
`.env` 内注释原文：「JWT 签名密钥与 OpenBase 侧共享（**`OPENBASE_JWT_SECRET` 同一来源**，不落 git）」。
· **判定**：OpenMemory **刻意启用了 JWT 第二层认证**，且密钥与 OpenBase **共享**。

-- 排查步骤 3：OpenLLM 出站形态（`app/edgerouter/adapters/openmemory_client.py`） --
· `set_auth_header()` 仅注入 `X-API-Key`（注释：R5 治理 Q1「内部直连统一 X-API-Key 形态」）；
· `set_outbound_headers()` 注入四维身份头 + `X-Proxy-Source` + `X-Request-Id`；
· **全流程不发送 `Authorization: Bearer`**（grep 确认该客户端无 Authorization 装配）。

-- 根因（唯一结论） --
**两侧契约在「顺序校验」上不兼容**：OpenLLM 按 R5 治理假设「OpenMemory 仅在配了 `api_key` 时才校验」，
故只发 `X-API-Key`；但 OpenMemory **同时启用了 JWT 第二层认证**（`OPENMEMORY_GATEWAY__JWT_SECRET` 已配，
密钥与 `OPENBASE_JWT_SECRET` 共享），而该层**强制且无法被 API Key 旁路** → 必然 401。
→ **不是** OpenMemory 故障、**不是** v1.4.8 会话编排逻辑缺陷，而是**跨系统鉴权形态未对齐**（集成缺口）。
→ 可佐证：OpenBase 侧配置项注释 `openbase/settings.py:166`「OpenLLM 对接（v1.4.3 R-379，
  **API Key Bearer 注入转发**）」——OpenBase 是**带 Bearer 形态**注入的，OpenLLM 出站到 OpenMemory 则不是。

-- 可选处置（**均属跨仓改动，本记录不擅自实施，待人工裁定**） --
方案 ①｜**OpenLLM 侧**：出站增加 `Authorization: Bearer <JWT>` —— 用**共享密钥**
  （与 `OPENBASE_JWT_SECRET` / `OPENMEMORY_GATEWAY__JWT_SECRET` 同源）签发服务账号 token，
  与既有 `X-API-Key` 并存；须确认 OpenLLM 侧可取得该共享密钥（现 `.env` 仅有 `SECRET_KEY`/`ALGORITHM`，**未确认同源**）。
方案 ②｜**OpenMemory 侧**：为受信来源（`X-Proxy-Source: openbase-…`）或该内部路径**豁免 JWT 层**
  （放宽安全姿态，须安全负责人确认）。
方案 ③｜**OpenMemory 侧**：把 `/api/v1/remember` 等内部契约路径纳入白名单（同 ② 的安全代价，最简）。
方案 ④｜**环境侧**：仅在联调环境**临时调整** OpenMemory 的 `GATEWAY__JWT_SECRET`/`ENABLED` 组合，
  使 `_enable_jwt=False`（**不推荐用于生产**，且与共享密钥设计相悖）。

-- 影响 --
① 「重启不丢写」（TT-v1.4.8-018）与三路回写闭合性（TT-v1.4.8-016）**仍无法取证**，阻塞点即此；
② `openllm_gateway.py` 增量覆盖补测同源受阻；
③ **本步骤未改动任何代码/配置**，仅只读排查与证据登记。

`GET /api/v1/monitoring/traces/{trace_id}/spans` → **500**；根因 `ResponseValidationError: 8 validation errors`（`traces.py:362`）。

-- 乙、根因定位（先读代码，再动手）--
`traces.spans` 列存在**两种历史写入形态**，而端点声明 `response_model=List[SpanResponse]`（必填 `span_id/name/kind/status`）：

| 形态 | 写入方 | 结构 |
|:----:|--------|------|
| ① **OTel 形态** | `trace_service.TraceContext`（`span_id/name/kind/status/duration_ms/...`） | 与响应模型一致 |
| ② **步骤计时形态** | 网关轻量写入（`[{"step": "auth", "ms": 0}, {"step": "llm", "ms": 10343}]`） | **缺 4 个必填字段 × 2 span = 8 项校验失败 → 500** |

**同一列承载两种结构**，故修复须在**读取侧归一化**（而非仅放宽响应模型 —— 放宽后形态②的字段会被静默丢弃，等于返回空壳）。

==================== 三十一、DEF-BE-148-012 修复与验证（RAG 装配缺失不得触发回退） ====================

-- 甲、缺陷回顾（§三十 戊）--
`TT-024`：配置 `OPENRAG_ENABLED=false` + `OPENRAG_FALLBACK_BUILTIN=true` 时，**适配器未注册却触发了内置回退**（实测 `degraded=[]`、`rag_source=builtin`），与 `DevLogReport` §13.1 **第十二批已批准语义**（未注册 → **组件级降级、不触发回退**）不符。

-- 乙、根因定位（读码，非猜测）--
| 位置 | 现状 | 语义 |
|------|------|------|
| `openllm_gateway._build_component_handlers._rag_handler`（`:341-370`） | 适配器调用外包 `try/except Exception`，**任何**异常（含 `ComponentUnavailableError`）都被吞并走内置回退 | ❌ 把「**装配缺失**（适配器未注册 / client 未注入）」与「**外部检索失败**」混为一类 |
| `component_pipeline.run_components`（`:112-117`） | `except (ComponentUnavailableError, asyncio.TimeoutError)` → **记降级、不回退**；仅其余异常才回退 | ✅ 这正是**已批准语义**（AC-148-03-1「两路径行为一致」） |

**结论**：缺陷在**网关 handler 包装层**未与共用组件步骤的语义对齐 —— 第十二批的语义变更只落到 `component_pipeline`，网关侧的 handler 包装仍是旧行为。
