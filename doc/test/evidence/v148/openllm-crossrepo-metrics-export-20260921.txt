==================== 三、实现要点 ====================

1) 流式路径接回执（工装 3 全路径覆盖）
   - 流式端点组装共用步骤返回值由 `_composition` 改为 `composition`（供回执使用）；
   - 流式循环内累积回答片段（`stream_answer_parts`，仅用于本地归因判定，不落库）；
   - 循环结束后调用 **同一构建入口** `build_receipt_from_result(...)`，
     写入 `routing_trace["context_metrics"]`，随 `_finalize_stream_trace`
     → `_save_trace` 落库（含断连 shield 路径）。
   - 结果：同步与流式两条路径的回执均落库（源码护栏断言 `"context_metrics"` 出现 ≥2 次）。

2) 批量导出接口（AC-148-01-1）
   端点：`GET /openllm/v1/trace/metrics/export`
   查询参数：`session_id` / `request_id` / `start_time` / `end_time` / `limit`（默认 200）
   返回：`{"items": [...], "total": n, "filters": {...}}`
   数据来源：`Trace.trace_metadata` → `routing_trace.context_metrics`；
   提取器 `extract_metrics_records(rows, session_id=, request_id=, limit=)`：
     - 仅返回含计量的行；无计量行与非法 JSON 行静默跳过（导出须健壮）；
     - 保持入参顺序（SQL 侧按 `Trace.start_time` 降序）；
     - 不修改行数据（仅观测）。

3) 查询/导出通道核实（更正前批表述）
   - 落库：`_save_trace` → `Trace.set_metadata({"mode","pipeline","routing_trace"})`
     → `db.commit()`（**已核实**，openllm_gateway.py:1412-1445）；
   - 既有查询：`app/api/traces.py` 前缀 `/monitoring`，
     `GET /monitoring/traces/{trace_id}` 返回 `trace.to_dict()`；
   - 新增批量导出：`GET /openllm/v1/trace/metrics/export`（本批）。
   - **更正**：前批证据引用 `_save_trace` docstring 中的 `/openllm/v1/trace/{request_id}`
     作为查询通道；经核对该 docstring 为**陈旧描述**（实际单条查询在 `/monitoring/traces/{trace_id}`），
     本批以实际路由为准。
