==================== 三、实现要点 ====================

1) 第三路（profile）纳入编排（AC-148-05-1）
   - `PipelineExecutor.execute` 新增 `profile_writeback` / `profile_writeback_kwargs`；
   - 调度条件：`profile_writeback is not None and llm_response`（空响应不回写，
     避免污染画像库；画像为固定注入段、不在 pipeline 组件内，故不要求组件存在）；
   - `ExplicitOrchestrator.run` / `AutoOrchestrator.run` 与网关编排助手
     `_run_orchestrated_chat`（explicit / auto 两分支）逐层透传。

2) 回调三路化（R-398 核心）
   `_build_writeback_callback` 返回 `(memory_cb, rag_cb, profile_cb, kwargs)`；
   队列不可用时三路均为 None（降级语义不变，主链路不受影响）。

3) 回写回执（AC-148-05-2）
   - 回调**返回 `queue.submit` 结果**（True=新入队=accepted / False=幂等命中=duplicated），
     使回执可区分受理状态；
   - 流式路径逐路记录 `routing_trace["writeback"] = {memory|rag|profile: {status, session_id}}`，
     通道异常逐路隔离（`failed` + 原因类型），**不影响主链路**；
   - 流式仅在回答非空时回写（与同步路径口径一致）。

4) 流式路径回写补齐（AC-148-05-4 / F-09 闭环）
   流式端点此前**完全没有回写**；本批在流式收尾前构造三路回调并按路提交，
   与同步路径共用同一回调构造（同一幂等键、同一持久化队列）。

==================== 四、遗留与边界（如实登记） ====================

1) **同步路径的逐路受理回执**：同步路径的回写由执行器以 asyncio 任务调度（fire-and-forget），
   网关侧不参与，故 `routing_trace["writeback"]` 目前**仅流式路径**逐路记录；
   同步路径的受理状态需经队列表（`writeback_queue.status/seq`）查询。
   → AC-148-05-2「回执覆盖率 100%」**部分满足**，缺口已显式登记。
2) **投递序号与「被丢弃项」**：seq 已由 F-08 修正为持久化来源；「被丢弃项标识」尚未落回执
   （当前无丢弃逻辑，属第二批裁剪相关，v1.4.9）。
3) R3（流式回写可行性）在本批按「收尾点聚合全文 + 逐路提交」实现；**端到端实测**
   （真实上游 + 真实队列 + 重启对照）属 Step 4 范围，未执行。
4) 第零段工装剩余 3 项：工装 5（归因 B 工具）、工装 6（固定集与评分表）、工装 7（汇总脚本）。
