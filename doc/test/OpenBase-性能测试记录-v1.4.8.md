## 3. 环境约束对口径的影响（须随结论一并阅读）

| # | 约束 | 实测证据 | 对判定的影响 |
|:-:|------|----------|--------------|
| C-1 | **网关全局限流 1 req/s（burst 60）** | 并发 8 突发实测：前 **67** 次 200，其后持续 `429 {"code":1003,"error":"rate_limit_exceeded","retry_after":1}`（首个非 200 出现在第 64 次） | **并发 8 档位在本实例上不可达成**；本轮改为客户端节流 `--rate 0.75`（低于全局限流）执行，**等价稳态串行负载**；并发 8 档位需在提高限流的**专用压测实例**另行执行 |
| C-2 | **语义缓存（阈值 0.92）** | 相同 prompt 第二次起 `timeline=[]`、`wall≈123ms`（命中缓存直接返回） | 每次采样注入唯一 nonce 规避；命中样本单列 `cache_hits` 且**不计入分位数**（本轮命中 0） |
| C-3 | **DPS 不可用** | `dps=unavailable`，健康探针 `latency_ms=2046`；同步对话存在 **~2.4~2.6s 未计量差额**（见 §5），与 DPS 连接等待量级一致 | 同步对话端到端显著抬高；因该等待**未进入 timeline**，**本仓开销与外部等待无法逐样本分离** → P-1 结论须附该限制 |
| C-4 | **模型池含未部署模型 + 成本优先选中**（**与错误率的关系已于 v1.1.0 更正**） | 池内 3 个本地模型**均不可达**：定点探测 `qwen3:0.6b` → **HTTP 500 / `5001 LLM 组件调用失败`**、`qwen2.5:0.5b` → **500**、`llama3.2:1b` → **500**；而 `deepseek-v4-flash` → **200**。三者价格均为 NULL（`float(None or 0)` = **0**）→ 成本因子最优 → 在「成本优先」下天然胜出 | ⚠️ **属性更正（v1.1.0）**：`routing` 事件中的 `"model":{"selected":"qwen3:0.6b"}` 是**路由前**取值（取自 `settings.DEFAULT_LLM_MODEL`），**不能**作为「实际调用模型」的证据；本轮压测失败请求的 trace 实测 **`model=deepseek-v4-flash` 且 `latency_ms=null`** → **两者不是同一问题**（详见 §6 #1/#6） |
| C-5 | **限流环境变量键名用错（v1.5.0 更正，C-1 已解除）** | 中间件实际读取 `RATE_LIMIT_ENABLED` / `RATE_LIMIT_PER_SECOND` / `RATE_LIMIT_BURST` / `RATE_LIMIT_USER_*` / `RATE_LIMIT_ROUTE_*`（`app/middleware/rate_limit.py::_load_config`）；而 `RATE_LIMIT_PER_MINUTE` / `RATE_LIMIT_PER_HOUR` 属**应用层设置**（`core/config.py`，仅供 `auth_service`）→ 调试期按后者提高限额**完全无效**，构成「以为已解除 C-1 实则未解除」，并导致一次单飞调试轮出现 429=124~178（该轮结果**已废弃**，未计入任何结论） | 专用实例按正确键名设置后，启动日志实证 `enabled=True, global=10000.0/s(burst=100000)`，**复测全部档位 429 = 0** | **C-1 解除**：并发 8 档在本轮**已达成**（`peak_in_flight = 8`）；**教训**：压测环境须以**启动日志实证**确认限额生效，不得仅凭环境变量已设置即认定 |
| C-6 | **SQLAlchemy `echo` 日志污染（v1.5.0 定位并关闭）** | `app/db/session.py` `create_engine(..., echo=settings.DEBUG)`；调试期 `DEBUG=true` → **每请求输出全量 SQL**（同步 I/O）→ 单飞档被拖慢至 ~2.3 s/请求（实测 519 次 GET 耗时约 20 min） | 置 `DEBUG=false` 后：单飞 P-6 P50 由 ~2300 ms 量级回到 **132.1 ms**；并发 8 档 `achieved_rps` 由 **1.578 → 9.317**（**5.9×**，同端点同口径） | 该污染曾使 v1.3.0 对「服务端串行化」的**量级**被高估；**定性不变**（并发 ×8 仅得吞吐 1.43×，串行化仍存在），详见 §4.5.3 与 §6 #7 |

### 4.4 TT-039：回执查询 @ 1e4 行（P-7）

**数据准备**：向同一 SQLite 队列 (`backend/data/writeback.db`) 播种 **10,000** 行（`session_id LIKE 'perf-tt039-%'`，`payload_json.user_id` 指向性能账号），队列 **140 → 10,140 行**（与轮次内自身回写增量 73 行合计 10,213 行）；播种脚本 `seed_receipts_1e4.py`（0.25s 完成），**清理方式**：`--cleanup`（按前缀精确删除）。

| 指标 | P50 | P95 | P99 | max | 目标 | 判定 |
|:----:|----:|----:|----:|----:|------|:----:|
| P-7 回执查询 @1e4 行（n=200，0 错误 / 0 次 429） | **236.5 ms** | **664.0 ms** | **864.8 ms** | 1128.6 ms | P95 ≤1000 / P99 ≤1500 | ✅ **达标** |

**规模效应对照**（同一端点、同参数、仅队列规模不同）：

| 档位（队列行数） | P50 | P95 | P99 | 倍率（对 140 行档） |
|------------------|----:|----:|----:|--------------------|
| 140 行 | 112.6 ms | 286.4 ms | 484.2 ms | 1.00× |
| **10,140 行** | **236.5 ms** | **664.0 ms** | **864.8 ms** | **2.10× / 2.32× / 1.79×** |

> **结论**：1e4 行档位**达标**（P95/P99 均在目标内，余量分别约 34% / 42%），**因此不登记技术债**；但规模从 140 → 10,140 行时 P95 增至 2.32×，呈明显退化趋势（`payload_json` 表达式过滤未建索引为已知项）——建议纳入容量观察项，在更大规模（≥1e5 行）压测前先评估索引化。
>
> **清理**：测量完成后已按前缀精确清理（`DELETE … WHERE session_id LIKE 'perf-tt039-%'`），**删除 10,000 行、残留 0**，队列回到 213 行（140 存量 + 73 本轮自身回写），**业务数据无残留**。

## 7. 结论与后续动作

**结论（v1.5.0 收口）**：以《非功能设计说明-v1.4.8》**v1.2.0 §1.1**（目标值 + **双口径**）为判据，`TT-v1.4.8-038` **未通过**，且**两项口径结论一致**：

- **单飞档**（节流 0.75 req/s）：达标 **P-3 / P-9 / P-12**；未达标 **P-1 / P-6 / P-8**；未判定 **P-4 / P-10**。
- **并发 8 档**（不限节流，`peak_in_flight = 8`）：达标 **P-3 / P-11**；未达标 **P-1 / P-6 / P-8 / P-9 / P-12**；未判定 **P-4 / P-10**。
- **`TT-v1.4.8-039` 仍通过**（P-7 @1e4 行：P95 664.0 ms / P99 864.8 ms，未重测，见 §4.4）。
- **首轮「受限口径」保留已消除**：C-1（全局限流）已按正确键名解除，并发 8 档已达成；P-11 已按同端点同口径基线判定；错误率由 13.3% / 6.7% 降至 **0%**（单飞档）。

**未达标项归因汇总**：**1 项本仓缺陷**（P-1：画像拉取降级无失败短路，≈ 2.04 s/请求，发现 #9）、**3 项架构债务**（P-6 / P-8 / P-9 在并发档，以及 P-12 并发档错误率，均归于 `TD-新增-027`）、**2 项数据规模效应**（P-6 / P-8，规模为基线 3.4~3.6×，发现 #13）、**1 项环境限制**（DPS 未启动，H 类，须与缺陷分别处置）。

**后续动作（按优先级）**：

1. **✅ `P-1` 缺陷修复（已完成，`v1.6.0`）**：`DT-148-019` 画像拉取降级路径已加**失败负缓存/短路**（`PROFILE_FAILURE_COOLDOWN_SECONDS`，默认 30 s）并提供**关闭画像注入**开关（`PROFILE_INJECTION_ENABLED`）；OpenLLM 提交 `ad7d472`，TDD 10 例护栏 + L1/L2/L3 验证。**定向复测**：本仓开销 P50 **2629.4 → 1157.9 ms（−56%）**。**未达预期（预期 ≤600 ms）如实登记**；**剩余动作**：待第 2 项计量接线后继续追残留 **1110.2 ms**。
2. **✅ `P-10` 计量接线（已完成，`v1.7.0`）**：`writeback_dispatch` 步骤已在**同步与流式两条路径**接线（OpenLLM 提交 `72fd01e`，5 例 TDD 护栏，回归与基线一致），`P-10` **口径缺口闭合并取得首次有效观测值**：**同步达标**（0.014~0.026 ms）、**流式不达标**（556~728 ms）→ 详见 §6.4。**遗留**：① 流式侧同步入队的处置（**`CR-148-020`**，待裁定）；② `P-10` 的**正式分位判定**仍须按每档 **≥200 请求**重跑 `TT-038` 后出数（本轮为 L3 冒烟，n=3/2，**不冒充分位**）。
2b. **`P-4` 计量接线（仍为口径缺口）**：`P-4`（SSE 首包本仓额外开销 P95 ≤100 ms）尚未接线 → 与 `TD-新增-027`（事件循环阻塞）同源，建议在 `TD-新增-027` 偿还时一并处置。
3. **`TD-新增-027` 偿还（架构，独立立项）**：并发 ×8 仅得吞吐 **1.43×**（达理想 17.9%）——`async` 路由内的**同步 SQLAlchemy / SQLite** 阻塞事件循环。措施：同步 DB 调用移入线程池 / 改异步驱动、**多 worker**、回执查询过滤下推。偿还后复测并发档 P-6 / P-8 / P-9 / P-12。
