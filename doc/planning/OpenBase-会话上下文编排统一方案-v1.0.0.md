## 1. 方案范围

本方案把此前分散在评估报告与咨询结论中的全部可选路线收归一处，给出比选结果、选定组合、实施链与改动面，作为后续跨仓派单与 Step 0 版本规划的单一输入。

不包含：具体版本排期与 Backlog 落位（由 Step 0 的范围决策确定）、前端会话界面的交互设计、模型选型的调整。

---

## 2. 设计原则与派生要求

原则由人工给定：以画像、记忆、知识库为基础把上下文补得更准，同时把投喂给 LLM 的 token 压得更省。

两条要求互相拉扯——更准要求多给，更省要求少给。编排的实质工作是**在固定预算内按相关性选择**，而非把素材拼长。由此派生四条要求：

| 要求 | 含义 | 现状 |
|------|------|:----:|
| 先排序后裁剪 | 裁剪必须发生在仍带相关性信息的结构化层面 | 不满足 |
| 预算含输出预留 | 预算 = 模型窗口 − 输出预留 − 安全余量 | 不满足 |
| 配额与竞争显式化 | 四类素材先给保底配额，余额按相关性竞争 | 不满足 |
| 裁剪可观测 | 丢弃了哪些片段、多少 token、原因，必须可查 | 不满足 |

## 3. 现状实测

### 3.1 编排能力已经在 OpenLLM 侧

`backend/app/edgerouter/orchestration/` 下已有组件路由器（R001~R005 规则 + 置信度 0.85 + LLM 兜底）、auto 编排器（A/B/C/D 四路径）、explicit 编排器（4001~4005 校验）、Prompt 组装器、管道执行器；`backend/app/api/writeback.py` 有三路回写（幂等 + 指数退避）；`backend/app/api/budgets.py` 有预算与额度；`backend/app/edgerouter/adapters/` 有 memory / rag / profile 适配器。入口为 `POST /openllm/v1/chat` 与 `/openllm/v1/chat/stream`。

网关侧 `openbase/modules/llm_proxy/__init__.py` 只做身份头组装与转发，无编排代码，本身就是薄层。

### 3.2 四类素材的真实形态

| 素材 | 产生方 | 进入 Prompt 的形态 | 关键问题 |
|------|--------|--------------------|----------|
| 画像 | `_build_profile_ctx` → ProfileAdapter | 字符串 | 可用 |
| 记忆 | `OpenMemoryAdapter.search` | 经 `format_context` 变编号字符串 | 原始结果带 `score`，在此步被丢弃 |
| 知识库 | `OpenRAGAdapter.search` | 同上 | 同上 |
| 会话历史 | 客户端 `messages` | **未进入** | 见 3.3 |

四类素材被 Jinja2 拼成单一字符串，再作为**唯一一条 user 消息**送入 LLM（`openllm_gateway.py:1122-1133`）。裁剪对象因此是片段级字符串，而 `ContextManager` 的裁剪能力是消息级，粒度不匹配。

### 3.3 会话轴缺位

| 事实 | 位置 |
|------|------|
| OpenAI 兼容通道只取 `messages` 中**最后一条 user 消息**作为 `query`，其余丢弃 | `openllm_gateway.py:995-1009` |
| explicit / auto 模式请求体无会话字段（`query` 为字符串） | `openllm_gateway.py:909-927`（`OpenLLMChatRequest` 无 `conversation_id`） |
| 前端发消息时只提交 `{ model, messages }`，不提交会话标识 | `openbase-ui/src/core/api/llm.ts:101`、`:113` |
| `ContextManager.get_context_window` 全仓无调用方 | `context_manager.py:582` |
| 网关链路零引用会话消息表 | `openllm_gateway.py` 无 `ConversationMessage` 引用 |
| 回写幂等键把「会话」记为「用户」 | `openllm_gateway.py:647`（`session_id = identity.user_id`） |

由此得到一条重要判断：**会话历史其实已经在请求里**（前端提交了 `messages`），只是 OpenLLM 侧把它丢掉了。这使「历史接入」可以在 OpenLLM 侧单独完成，不必等待前端改造。

### 3.4 回写幂等键缺陷（F-08）

`_next_writeback_seq` 使用进程内内存计数器（`openllm_gateway.py:620-626`，注释自承「重启后归零」），队列表为 `UNIQUE(session_id, seq, target)` + `INSERT OR IGNORE`（`writeback_queue.py:83`、`:110-130`），`submit` 在幂等命中时直接返回 False 且不执行（`:314-322`）。进程重启后计数器归零，某用户历史上有 N 次回写，重启后其**前 N 次回写全部静默丢弃**，响应仍报 `duplicated=true`；启动恢复只重跑已入库行，不回填计数器。

OpenLLM 自己在 v2.13.0 的代码逻辑审查记录中已就同一缺陷类定性为 **P1**（R-003：seq 缺省固定 1 → 第二轮起回写丢失），修复只落在 `api/writeback.py`（改用 `max_seq+1`），编排侧未同步。DB 侧已有可用的 `max_seq(session_id)`（`writeback_queue.py:230`）。

> 本条为代码推演结论，尚未实机复现。定级登记前需按受控重启复现确认。

## 4. 已评估方案全集与比选结果

### 4.1 编排归属

| 方案 | 落点 | 结论 | 主要理由 |
|------|------|:----:|----------|
| A 网关侧新建编排层 | OpenBase 网关 | 不采纳 | 与既有编排重复；网关热路径新增三个跨服务依赖；SSE 变两跳组装；网关侧从零构建 |
| **B 复用并扩展 OpenLLM 既有编排** | OpenLLM | **采纳** | 引擎、适配器、回写、预算、上下文计量均已在位；变更面最小；不触四仓边界 |
| C 引入 LiteLLM 作编排框架 | OpenLLM（替换） | 不采纳 | 能力高度重叠形成双路由权威不明；身份与隔离契约不匹配；缺口（上下文装配）恰是它不提供的 |
| D LiteLLM 作 upstream adapter | OpenLLM 之下 | 条件性保留 | 仅在需接百级外部供应商且 registry 覆盖不足时评估；引入但不接管编排 |

早期「A 方案」建议已撤回。误判根因是「聚合编排」一词在两侧同名不同物：网关侧指业务数据 BFF 跨系统取数（G3），OpenLLM 侧指 LLM 调用链上下文装配。

### 4.2 预算裁剪实现

| 方案 | 结论 | 理由 |
|------|:----:|------|
| A 复用消息级 `manage_context` | 不采纳 | 粒度错配，单条消息场景下不裁剪；换 `recent` 策略且超限时返回空列表 |
| B1 片段级 + 按条目尾截断 | 过渡可用 | 匹配真实形态、改动小，但只满足省 token，精准不足（依赖「编号列表尾部即低分条目」的隐含假设） |
| **B2 结构化片段 + 配额保底 + 相关性竞争** | **采纳** | 与 §2 原则一致：先排序后裁剪，配额与竞争显式化 |
| C 适配器层前置裁剪 | 不采纳 | 适配器不掌握最终模型与输出预留，算不出正确预算；策略分散 |

B1 曾在本方案前一版被推荐为首选，按 §2 原则修正为过渡形态：B2 为终态，B1 可作为第一个迭代的落地起点。

### 4.3 会话轴归属

| 方案 | 结论 | 理由 |
|------|:----:|------|
| 并入 R-395 | 不采纳 | 与预算裁剪作用方向相反（会话轴补素材、预算裁剪减素材）；先减后加需重调配额；一个需求同时改「给什么」和「给多少」，故障无法二分 |
| **独立成条并作 R-395 前置** | **采纳** | 依赖方向清晰；验收可独立（历史是否进入上下文可直接观测）；会话轴自带历史窗口，不引入超窗 |

### 4.4 双路径

| 方案 | 结论 | 理由 |
|------|:----:|------|
| 保持分叉，两处各实现 | 不采纳 | 每项编排改动都要写两遍，行为必然漂移；F-08 类修正对流式路径无效 |
| **收敛为共用步骤** | **采纳** | 流式路径当前绕过 `PipelineExecutor`，且无回写、无语义缓存、`model="auto"` 不走 5 因子路由与 fallback（F-01）；不收敛则后续每项都翻倍 |

### 4.5 统一选定组合

**方案 B（编排归 OpenLLM）+ B2（结构化片段与预算竞争）+ 会话轴独立前置 + 双路径收敛。** 该组合即本方案的实施对象。

## 5. 统一方案设计

### 5.1 目标形态

会话是上下文的累积单位与预算的记账单位；画像、记忆、知识库、会话历史四类素材在**同一份会话预算**下竞争；编排负责选择与渲染，会话负责状态、序号与幂等。

### 5.2 三段实施链

| 段 | 内容 | 为什么在这个位置 |
|:--:|------|------------------|
| 前置零 | 双路径收敛（R-397，含 F-01） | 不收敛则后续每项都要双份实现，且行为漂移 |
| 第一批 | 会话轴接入（R-396）+ 回写幂等键修正（F-08） | 同属会话维度，天然同批；会话轴以 `get_context_window` 对历史做窗口，不引入超窗 |
| 第二批 | 结构化片段 + 预算裁剪 + 可观测回执（R-395，含 F-02、F-06） | 输入集合已完整，配额与竞争规则只需调一次 |

### 5.3 各段设计要点

**前置零（双路径收敛）**

把「组件执行 → 上下文格式化 → 预算 → 组装」抽为共用步骤，供 `/chat` 与 `/chat/stream` 共用；流式路径补齐回写与缓存语义，或显式声明不提供并写入契约。`model="auto"` 与 `mode="auto"` 在两路径行为一致。

**第一批（会话轴）**

OpenLLM 侧把 `messages` 的历史按窗口纳入上下文——用 `ContextManager.get_context_window` 或等价的按 `max_tokens` 截取，而非只取最后一条 user 消息；`OpenLLMChatRequest` 增加会话标识字段；回写幂等键由 `user_id` 改为会话标识，`seq` 改用 DB 侧 `max_seq + 1`（替换进程内计数器）。会话标识字段为可选，缺省时退化为按用户记账，保持既有调用方兼容。

**第二批（预算与选择）**

`format_context` 之前保留结构化片段（含 `score`、来源、时间）；预算取 `(get_model_context_limit(model) − 输出预留) × 安全余量`；四类素材先给保底配额，余额按相关性竞争；裁剪按条目切分而非按字符切分，单条超预算时做文本级截断并标记；裁剪后二次计数校验，仍超预算则显式降级，不放行也不静默丢弃。

### 5.4 可观测回执

`routing_trace` 增补预算回执：模型、窗口、输出预留、实际预算、裁剪前后 token 数、被丢弃片段清单与原因、是否发生硬截断。无回执视为该段未完成——否则「精准」既无法验证也无法调优。

## 6. 改动面与跨仓边界

问题「是否所有改动都在 OpenLLM 侧」经核实**不成立**，实际为三方触达。

| 触达方 | 需要的改动 | 依据 |
|--------|------------|------|
| **OpenLLM（主体）** | 编排与预算能力、会话轴接入、双路径收敛、回写幂等键修正、窗口前缀匹配修正 | §3 全部实测 |
| **前端（openbase-ui）** | 发消息时提交会话标识（当前只提交 `{ model, messages }`，`llm.ts:101`、`:113`）；历史已随 `messages` 提交，无需改造 | 同上 |
| **本仓文档** | R-394 的编排 DSL 边界定界（口径整合，不涉代码） | 上游评估报告 §6 |
| **OpenBase 网关** | **无需改动**——`llm_chat(payload: dict[str, Any])` 原样转发请求体（`llm_proxy/__init__.py:355-366`），新增字段直接透传 | 代码实测 |

由此得到对第二个问题的准确回答：**在 OpenLLM 侧以「会话」为迭代主题归集这些方案是合理的，但不应把它们都归到「会话模块」里实现。** 编排还依赖模型路由（`core/router.py`）、组件适配器、配额中间件与语义缓存，这些不在会话域；预算裁剪的落点在 `orchestration/`，双路径收敛的落点在网关入口。硬合会让会话模块承担全部职责。

主题归集与模块归属是两件事：**主题按「会话」归集（一个迭代主题下挂 R-395 / R-396 / R-397 与 F-02 / F-06 / F-08），实现按模块落位（会话域 / 编排域 / 网关入口）。**

本仓不实施上述 OpenLLM 侧改动（`VC-014`），一律走跨仓派单。

## 7. 登记与承接建议

登记载体的判据：既有债务走技术债务总表（TD）；发布期发现的缺陷走问题跟踪记录（DEF）；能力缺口与设计取舍走候选需求池（R）；跨仓执行走 `doc/planning/` 派单项。本轮各发现均为评估期发现的既有缺口，非 v1.4.7 发布缺陷，故主要归 TD 与 R。

| 对象 | 载体 | 级别 |
|------|------|:----:|
| 会话轴缺位（F-07） | 候选需求池 R-396（本体即需求，不另建 TD） | P2 |
| 双路径分叉（F-01） | 候选需求池 R-397 + 技术债务总表（架构一致性） | P2 |
| 窗口前缀匹配（F-02） | 随 R-395 修正，不单独建 ID | P2 |
| 裁剪方法不二次校验（F-06） | 随 R-395 修正，不单独建 ID | P2 |
| 回写幂等键（F-08） | 技术债务总表（建议立即登记）+ 派单项修正项 | P1 |
| 固定 1000 配额、死参数、system_prompt 恒空（F-03~F-05） | 仅记录于评估报告 | P3 |

F-08 建议走立即登记而非「延后到版本收口复核」的既有范式：该范式的理由是避免归属未定的设计议题反复改版，而 F-08 定性明确（他仓已有 P1 先例）、范围固定，不属于该情形。前提是先复现。
