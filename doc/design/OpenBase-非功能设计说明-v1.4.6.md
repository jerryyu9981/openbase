## 2. 性能与容量设计

| 项 | 目标 | 设计手段 |
|----|------|----------|
| 检索响应 | 单次 **P99 < 2s**（默认 24h 窗、`page_size=20`、单源） | ① L1：分片**倒序**选择 + 命中足量**提前终止**（不足整窗才回退扫描更多分片）；② DB：过滤条件**尽量下推 SQL**，`COUNT` 与取页分两步；③ 不做跨源并行（单请求仅一个源，天然隔离） |
| 扫描上限 | ≤ **2 个日分片** / ≤ **200,000 行** | settings 可配（`log_query_max_days` / `log_query_max_lines`）；触顶置 `truncated=True` 并返回 200 |
| 分页上限 | `page_size` ≤ 100 | Pydantic 约束，越界 400（避免深分页拖垮 L1 扫描） |
| 导出上限 | ≤ 10,000 条 | 超限 400 + `detail={matched, limit}`；导出采用**流式写**（`StreamingResponse`）避免整份驻留内存 |
| 容量 | **零新增持久化** | 不新增表/文件；仅新增 `audit_logs` 中 `action=log.export` 行（每次导出 1 行，量级可忽略） |
| 内存 | 单请求驻留受控 | L1 逐行处理（不一次性载入整文件）；导出分块写出 |
| 并发 | 不引入新瓶颈 | 只读路径；不新增锁与共享可变状态；沿用既有网关与 ASGI 并发模型 |
| **四仓日志源（`repo_log`）**（v1.1.0） | 不劣化 P99 < 2s | ① **复用 L1 同一套机制**（日分片倒序 + 命中足量提前终止 + 上限截断），不另写扫描策略；② 扫描上限按**目标 svc 目录**独立计算（非四仓合计），避免单仓体量大时挤占预算（系统架构 ADR-146-06）；③ **解析成本**：JSONL 逐行 `json.loads` 优先，**纯文本回退**按行正则解析（回退路径成本更高，仅作过渡）；④ **实测体量（dev 强度，1~2 天）**：`openllm` 1.57 MB > `dps` 191 KB > `openmemory` 39 KB > `openrag` 15 KB，**四仓合计 ≈1.82 MB**；⑤ **生产须按 QPS 重估**（风险 13），并复核扫描上限与 `truncated` 提示是否需按新源调参 |

**瓶颈路径与预算**：L1 首次扫描是该功能唯一显著成本路径（无索引）。预算：以 420 B/行估算，200,000 行 ≈ 84 MB 顺序读；本机 SSD 量级下 <1s，余量用于 JSON 解析与过滤。

## 3. 安全设计

| 项 | 设计 |
|----|------|
| 威胁建模（STRIDE 摘要） | **S**poofing：复用 JWT 认证，无新身份路径 → 既有风险不变；**T**ampering：只读接口 + 参数化查询 + 枚举白名单；**R**epudiation：导出留痕 `log.export`；**I**nformation disclosure：脱敏 + 仅管理员 + 路径白名单（三项硬控制）；**D**oS：`page_size`/导出/扫描上限三重限幅；**E**levation：单一权限码 `log:read`，不新增角色嵌套 |
| 数据分类分级 | 日志含 **PII**（操作人 ID、客户端 IP）与**运维细节**（路径/状态码/上游摘要）→ 定级"内部-受限"，仅管理员可读可导出 |
| 鉴权 | `Depends(require_permission("log:read"))`；无令牌 401 `AUTH_401`，无权 403 `PERM_403` |
| 授权边界 | 跨租户可见（决议 1）——**在代码注释与测试中显式声明**，防后续误加 tenant 过滤导致"看得到却查不到"的隐性降级 |
| 脱敏 | 服务端复用 C-18 `mask_sensitive`：`Authorization`/`api_key`/`password`/`token` 等键 → `[MASKED]`；`summary` 只保留白名单键；前端零脱敏职责 |
| 路径安全 | 文件名由代码按时间窗生成 + 白名单正则 `^openbase-\d{8}\.jsonl$` + `Path.resolve()` 后目录归属校验（三重）→ AC-146-07-3 |
| 注入防护 | SQL 全参数化（`select().where()`）；无字符串拼接；关键字长度 ≤200 且不参与路径/SQL 结构 |
| 检索词不留痕 | `q` 仅用于过滤，不写入 L1 与 `audit_logs`（AC-146-03-3） |
| 安全需求追溯 | AC-146-06-3/06-4/07-1/07-2/07-3/07-4 全部有对应设计条目（本节 + 系统架构 §6） |
| **模块开关权限**（v1.1.0） | 新权限码 **`module:manage`**（仅管理员）；接口 403 + 页面/入口不可见（AC-146-15-2）；**每次变更强制留痕** `audit_logs(action=module.switch)`（操作人 / 模块 `id` / 前后状态，AC-146-15-3）；**不改注册表语义**（AC-146-15-4） |
| **四仓日志脱敏**（v1.1.0） | 四仓日志经 `RepoLogAdapter` **服务端统一脱敏**，**不得因新源放宽口径**（AC-146-19-3）；四仓 JSONL 中 `token`/`authorization`/`api_key` 等键 → `[MASKED]`；**沿用各仓既有脱敏逻辑**但不依赖它（本仓再兜一层） |
| **跨仓信任边界**（v1.1.0） | 四仓日志为**他仓产物**，本仓按"**不可信输入**"处理：逐行解析失败即跳过（不抛出）、字段长度截断、不做任何代码执行/模板渲染；`X-Request-Id` 透传仅影响他仓日志字段，**不参与本仓鉴权**（AC-146-16-2 拒伪造） |

## 4. 可观测性设计

> 按 `observability-standards` 四要素逐项核对（本版本**不扩充**标准，只做适配）。

| 要素 | 标准要求 | 本版本落地 |
|------|----------|-----------|
| 日志结构 | 结构化 JSON（traceId/spanId/service/module/message） | ✅ 三端点请求经既有审计中间件落 L1 `api.request`（含 `request_id`/`actor`/`path`/`status_code`/`duration_ms`）；**零额外代码** |
| 关键指标（14 种） | http_requests_total / http_request_duration_seconds 等 | ✅ 复用既有指标口径（请求级指标由既有中间件覆盖）；本版本**不新增业务指标**；`truncated` 次数可作为后续指标化输入（已登记为建议，非本版本范围） |
| 链路追踪 | OTLP + W3C TraceContext | ✅ 沿用既有 `X-Request-Id` 贯通与响应体 `request_id`；未引入新追踪协议 |
| 必备 Dashboard（6 个） | Service Overview 等 | 🚫 不适用（本版本排除"统计看板"）；日志中心页面本身即排障入口 |
| 错误码 | 统一前缀与格式 | ✅ `PARAM_400`/`AUTH_401`/`PERM_403`/`SYS_503`/`SYS_500`，响应体含 `request_id` |
| 排障上下文 | ✅ ① 单源降级返回 `source` + `request_id`；② L1 坏行跳过并计数（不静默）；③ 导出留痕含 `row_count`；④ 截断态显式提示 |
| **四仓源可观测性**（v1.1.0） | ✅ ① 四仓日志经既有审计中间件**被动入日志中心视野**（其请求本身即 `l1_file` 记录）；② `repo_log` 解析失败/未知 svc 目录 → `WARN` **并计数**（不静默）；③ 某仓未接线时该仓 `request_id` 为 `null`（**可见的缺失**而非伪造）；④ 覆盖状态须在交付说明**逐仓列明**（AC-146-20-3） |

## 5. 可靠性与降级设计

| 场景 | 设计 |
|------|------|
| 单源不可用 | 该源 `SYS_503` + `items=[]`；**不跨源自动兜底**（避免用户以为在看 A 源实为 B 源） |
| L1 文件不存在 | 返回空列表 + `total=0` + 200（非错误；当日无日志属正常） |
| L1 坏行 | 逐行解析失败即跳过并计数，**不中断整批**（日志文件可能被并发写入，尾行可能不完整） |
| DB 连接失败 | `SYS_503`；不重试风暴（单次请求内不重试） |
| 导出留痕失败 | **不阻断导出**（降级：`WARN` 记录后继续返回文件）→ 保证"取数据"优先于"记行为" |
| 截断 | 200 + `truncated=true`（不是错误）；语义显式，禁止静默不完整 |
| 幂等 | 全部端点 GET 且无副作用（唯一边写为留痕，且重复导出产生多条留痕属预期） |

## 6. 兼容性与可维护性设计

| 项 | 设计 |
|----|------|
| 契约兼容 | 不修改任何既有端点契约与字段；错误码体系沿用 |
| 依赖 | **不新增第三方依赖**（Python 3.10 / FastAPI / SQLAlchemy / Vue3 + Element Plus 既有） |
| 前端兼容 | 新增 1 页 + 1 条重定向；不改动既有页面与路由语义（`/system/audit` 仍可访问，仅重定向） |
| 分层可维护 | Controller（校验）/ Service（编排）/ Derivation（派生单点）/ Repository（适配器）/ Schemas（契约）；适配器**可插拔**：新增源 = 新增适配器 + 注册枚举 |
| 可测试性 | 适配器可注入替身（Step 3 以假文件/假会话/假服务做单测）；派生规则表驱动（枚举映射用例） |
| 命名与规范 | 遵循 `universal-naming-conventions` 与 `AGENTS.md`（snake_case 模块、PascalCase 类、UPPER_SNAKE 常量） |
| 可配置 | 4 个 settings 项（窗口/分片/行数/导出上限）集中可调，避免硬编码 |

## 7. 不适用项说明

| 项 | 原因 |
|----|------|
| 缓存设计 | 日志查询为"实时可观测"场景，缓存会带来陈旧与口径不一致风险；且本版本目标是可用而非极速 → **不引入缓存**（如需另立需求） |
| 消息队列 | 无异步解耦需求（只读查询 + 一条留痕写入） |
| 容量扩容设计 | 零新增持久化结构，无扩容诉求 |
| 告警与 Dashboard | 需求明确排除（本次诉求为"分类查看与检索"） |
| 可访问性专项（WCAG 全量） | 仅新增 1 页，按《UI设计文档-v1.4.6》§7 四项要求执行；不做全站无障碍专项 |
