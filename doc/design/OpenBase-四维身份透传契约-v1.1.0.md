## 1. 契约目的与范围

### 1.1 背景与问题陈述

OpenBase 统一前端/调用方经代理链（memory-proxy / llm-proxy / rag-proxy）访问四系统时，四维身份（用户、租户、团队、智能体）的透传存在以下已核实缺陷：

| # | 缺陷 | 证据 |
|---|------|------|
| P1 | JWT 仅携带用户 + 租户（org_id 为租户别名），**无 team_id / agent_id** | `openbase/modules/auth/__init__.py` 登录签发 `extra={"org_id": tenant_value, "role": role}` |
| P2 | memory-proxy 注入 `X-Org-ID`（值=租户）与 `X-Tenant-ID` 同值，语义混用；缺 `X-Team-Id/X-Agent-Id` | `openbase/modules/proxy/memory_proxy.py` `_build_upstream_headers` |
| P3 | llm-proxy / rag-proxy **零身份注入**；rag-proxy 对应 OpenRAG 无认证，登录用户可访问全部知识库 | `openbase/modules/llm_proxy/__init__.py`、开发需求文档-v1.4.4 §3.2 |
| P4 | 四维身份头解析能力（R-369 `IdentityContext`）已实现但**仅接入审计模块**，未接入任何代理链 | `openbase/core/deps/auth.py` `get_identity_context` 调用方仅 `openbase/modules/audit` |
| P5 | 团队管理（R-376）、智能体管理（R-377）顺延 v1.5，四维身份源头无实体管理 | 版本迭代路线图 §2.5 |

### 1.2 契约目标

| # | 目标 | 验收对应 |
|---|------|---------|
| G1 | 身份上下文在链路每一跳**显式存在**（4 段定长 scope，允许占位符），不允许字段缺失 | §5/§6/§7 强制规则 |
| G2 | 头注入**单一实现点**（OpenBase 网关/ProxyBase），代理只透传不改写 | §7.3 |
| G3 | 数据隔离 = 层级即可见性：**tenant 等值 + scope 前缀匹配**，隔离与共享同一机制 | §4.3/§7.4 |
| G4 | 各系统声明数据层级落点（隔离策略声明），不各自发明过滤逻辑 | §10 |
| G5 | 消除 X-Org-ID 语义混用 | §6.3 迁移 |
| G6 | 契约可由测试/CI 强制校验（缺头即失败、前缀越权即失败） | §12 测试与验收 |

### 1.3 适用范围

- OpenBase 认证模块（JWT 签发/校验）、统一网关（/api/v1/proxy）、三个专用代理（memory/llm/rag）及未来 DPS 代理
- 统一前端 openbase-ui（请求层携带与消费身份上下文）
- 四个上游系统（OpenLLM v2.13.0 / OpenRAG v1.8.0 / OpenMemory v6.8.0 / DPS）

### 1.4 边界与排除项

| 排除项 | 说明 |
|--------|------|
| 团队/智能体管理 API 设计（R-376/R-377） | 属于实体管理需求，本契约只定义其在身份上下文中的透传形态 |
| 各系统数据层隔离的数据库实现细节 | 本契约只定义"tenant 等值 + scope 前缀"义务与验收，实现由各系统设计 |
| 服务级 API Key 通道（/api/v1/proxy 双通道） | Key 通道不携带用户身份，沿用现状（R-367），不在本契约扩展 |
| 组织（org）独立维度 | 本期 org 并入租户（X-Org-ID 废弃）；如未来引入独立组织维度需契约升版 |

## 2. 核心概念与术语

| 术语 | 定义 |
|------|------|
| 四维身份 | 用户（User）/ 租户（Tenant）/ 团队（Team）/ 智能体（Agent）四个身份维度 |
| 组织树 | 租户 → 团队 → 用户 → 智能体的四层归属结构 |
| 数据 Scope | 数据行标记的层级归属键 `{tenant}/{team}/{user}/{agent}`，4 段定长，无则 `-` 占位 |
| 占位符 | 段值 `-`：表示该层级无归属（无团队/无智能体/用户级数据），值域保留，禁止业务使用 |
| 层级即可见性 | 数据落在组织树某节点，可见范围 = 该节点整棵子树；查询用前缀匹配实现聚合/隔离 |
| 可见前缀集合 | 当前身份可访问的 scope 前缀集合（个人域 + 名下智能体域 + 所属团队域 + 租户域，按角色裁剪） |
| 前缀匹配 | 查询 `tenant_id = ? AND scope LIKE '前缀%'`（参数转义 `%`/`_`） |
| 隔离策略声明 | 各系统/数据域声明自身数据在组织树上的层级落点（§10） |
| fail-closed | 身份上下文缺失/越权前缀时拒绝请求（401/403），而非放行 |
| 单一实现点 | 身份头注入与 scope 推导只存在于 OpenBase 网关/ProxyBase 一处 |
| IdentityContext | R-369 已实现的四维身份解析数据结构（openbase/core/deps/auth.py），本契约扩展其消费范围 |

## 3. 契约总则

### 3.1 "身份必选"的定义

> **身份上下文在认证链路每一跳上必须显式存在。允许承载占位符（§4.4），不允许字段缺失、不允许语义漂移、不允许代理自创头。**

- "显式存在"：JWT payload 与透传头中身份字段必须出现，且可解析出确定值。
- "不允许语义漂移"：同一维度在链路各跳含义一致（如 org 不得在代理处被当作 team 使用）。
- "不允许自创头"：除 §6.1 定义的头外，代理不得发明/改写身份头。

### 3.2 层级即可见性（核心原则）

1. 数据行写入时标记**一个且仅一个** scope（落在组织树某节点）。
2. 可见性 = 前缀包含关系：前缀 P 可见数据 D ⇔ D.scope 以 P 开头（或相等）。
3. 隔离 = 前缀边界：不在可见前缀集合内的数据不可见，且查询层强制（服务端过滤，不依赖前端）。

### 3.3 强制失效原则

任一跳检测到身份缺失/非法/前缀越权 → 立即拒绝（fail-closed），不允许降级放行。静默降级视为契约违规。

## 4. 身份与组织树模型

### 4.1 组织树

```
租户 tenant
  └── 团队 team（可空 → 占位符 `-`）
        └── 用户 user
              └── 智能体 agent（可空 → 占位符 `-`）
```

- 用户属于租户（必选）；用户可属于 0..N 团队（主团队用于 scope 定位）。
- 智能体属于用户；数据归属粒度 = 团队共享（team 层）/ 用户私有（user 层）/ 智能体私有（agent 层）。

### 4.2 数据 Scope 规范

| 项 | 规范 |
|----|------|
| 格式 | `{tenant_id}/{team_id}/{user_id}/{agent_id}`，4 段定长，恒以 `/` 分隔 |
| 占位 | 无团队 → `-`；无智能体 → `-`；用户级数据 → agent 段 `-` |
| 值域 | 各段 `^[a-zA-Z0-9_]{1,64}$`；**禁止** `-`（保留占位符）、`/`、`%`、`_`（`_` 与 `%` 防 LIKE 通配注入）、空格、控制字符 |
| 定长原因 | 前缀从固定位置切分，杜绝"无团队用户 vs 团队 ID"的变长歧义 |

### 4.3 可见前缀集合

当前身份（principal）的可见前缀集合由网关/身份服务推导：

| 来源 | 前缀 | 说明 |
|------|------|------|
| 用户私有域 | `{tenant}/{team}/{user}/` | 本人个人数据 + 名下全部智能体（**用户看自己不同智能体 = 此前缀**） |
| 名下智能体域 | `{tenant}/{team}/{user}/{agent}` | 精确到单个智能体（子集，无需单独列） |
| 所属团队域 | `{tenant}/{team}/` | 团队共享数据（按角色裁剪：成员/管理员） |
| 租户域 | `{tenant}/` | 租户管理员 |

推导关系（owned）：用户拥有的 agents/teams 由身份服务按需解析（**不强制入 JWT**，防 token 膨胀），网关持有绑定关系缓存完成"当前上下文 scope 推导与注入"。

### 4.4 默认规则

- 无团队：team 段 = `-`（不注入默认团队实体）。
- 无智能体：agent 段 = `-`，用户个人域即 `{tenant}/{team}/{user}/`，天然用户级隔离——**废弃 v1.0.0 的全局默认实体方案**（该方案存在"不同用户落入同一默认域导致混同"缺陷，见 §17 修订记录）。

## 5. JWT 契约

### 5.1 Claims 规范

| Claim | 类型 | 必选 | 说明 |
|-------|------|:----:|------|
| `sub` | string | 必选 | 用户 ID（四维之"用户"） |
| `username` | string | 可选 | 用户名（冗余） |
| `tenant_id` | string | 必选 | 租户编码；签发时强制非空 |
| `team_id` | string | 必选 | 主团队编码；无 → `-` |
| `agent_id` | string | 必选 | 当前上下文智能体编码；无 → `-` |
| `role` | string | 可选 | 用户角色（RBAC） |
| `org_id` | string | 废弃 | 迁移期与 `tenant_id` 同值；v1.5 全量切换后移除 |
| `permissions` | array | 可选 | 权限点（沿用现状） |

> 用户拥有的 agents/teams 集合**不入 JWT**（§4.3），由网关/身份服务按需解析。

### 5.2 签发规则（强制）

1. `create_access_token` 必须携带四维 claims（`sub`/`tenant_id`/`team_id`/`agent_id`），任何维度缺失即拒绝签发并记录审计。
2. `tenant_id` 从用户实体读取；无租户用户由租户管理（R-374）约束，禁止签发（不默认注入）。
3. `team_id`/`agent_id` 从用户绑定关系读取；未绑定写入 `-`（占位符）。
4. 刷新（refresh）签发的 access token 必须与原始签发的四维一致（refresh token 携带并回填四维）。

### 5.3 校验规则

- `decode_access_token` 后必须校验四维 claims 完整性；缺失即视为无效 token。
- 校验函数收敛为单一实现（如 `validate_identity_claims(payload) -> IdentityContext`），供 `get_current_user`、各代理复用。

### 5.4 兼容与废弃

| 阶段 | 动作 |
|------|------|
| 契约生效期（双写） | JWT 同时携带 `team_id`/`agent_id`（新）与 `org_id`（旧，值=tenant_id），保证存量消费方不破 |
| v1.5 全量切换后 | 移除 `org_id`；继续依赖 `org_id` 的调用方视为契约违规 |

## 6. 透传头契约

### 6.1 头规范（三头）

| 头 | 必选 | 来源 | 用途 |
|----|:----:|------|------|
| `X-Tenant-Id` | 必选 | JWT `tenant_id` | 租户等值过滤（独立列，不参与 LIKE） |
| `X-User-Id` | 必选 | JWT `sub` | 用户标识（审计 + 前缀推导） |
| `X-Scope` | 必选 | 网关推导的当前上下文 | 4 段定长 `{tenant}/{team}/{user}/{agent}`，前缀匹配的查询基 |

> `X-Team-Id`/`X-Agent-Id` 不再单独透传（由 `X-Scope` 承载）；如需审计精确维度，上游可解析 X-Scope 各段。`X-Org-ID` 见 §6.3。

### 6.2 注入规则

1. **单一实现点**：网关/ProxyBase 统一完成"JWT 校验 → 身份绑定解析 → 当前上下文 scope 推导 → 三头注入"；三个代理（memory/llm/rag）及未来 DPS 代理**只透传不改写**。
2. 所有经 OpenBase 转发至上游的请求（含 `/api/v1/proxy/{system}/*` 与三个专用代理端点）必须携带三头。
3. 推导失败（如绑定关系缺失）→ 401/403（fail-closed），不允许注入默认值放行（占位符 `-` 是显式声明的合法值，与推导失败不同）。

### 6.3 废弃头迁移（X-Org-ID）

| 阶段 | 动作 |
|------|------|
| 现状 | memory-proxy 注入 `X-Org-ID`（值=tenant_id）——**语义混用缺陷** |
| 契约生效期（双写） | 同时注入 `X-Org-ID`（兼容，值=tenant_id）与 `X-Scope`（正确语义）；OpenMemory 侧按 §9 对齐 |
| v1.5 全量切换后 | 停止注入 `X-Org-ID`；上游仍消费 `X-Org-ID` 视为对接缺陷，由消费方跟进 |

## 7. 链路各跳强制规则

### 7.1 链路结构

```
统一前端/调用方（携带 JWT）
  → ① OpenBase 认证签发（四维 claims 全量签发，§5）
  → ② 网关/ProxyBase（身份绑定解析 + 上下文 scope 推导 + 三头注入，§6.2）
  → ③ 上游系统（tenant 等值 + scope 前缀匹配过滤，§7.4）
```

### 7.2 第 1 跳：OpenBase 认证签发

- 义务：§5.2 签发规则、§5.3 校验规则。
- 强制校验：登录/刷新后 JWT 四维 claims 完整性测试（§12 TC-JWT-001）。

### 7.3 第 2 跳：网关/代理（唯一注入点）

- 义务：校验 JWT → 解析身份绑定（owned teams/agents）→ 推导当前上下文 scope → 注入三头 → 转发；推导失败/缺四维 → 401/403（fail-closed）。
- 禁止：代理内自定义身份提取逻辑、改写/映射身份头、选择性注入、注入默认值掩盖推导失败。
- 现有三代理改造范围：
  - memory-proxy：删除自研 `_extract_identity`/`_build_upstream_headers` 中的身份部分，改调统一注入器；补 `X-Scope`；`X-Org-ID` 进入双写迁移。
  - llm-proxy：新增三头注入（当前零注入）。
  - rag-proxy：新增三头注入 + 租户级白名单（OpenRAG 无认证期间，§9）。

### 7.4 第 3 跳：上游系统消费

- 过滤义务：所有数据访问（列表/详情/写操作/检索）必须 `WHERE tenant_id = ? AND scope 前缀匹配`；无过滤的查询视为 P0 缺陷。
- 前缀匹配实现：`scope LIKE '{prefix}%'`，**参数必须转义 `%`/`_`**（§4.2 值域已禁，双保险）；`tenant_id` 独立列等值，不参与 LIKE（防跨租户）。
- 校验：缺失三头/前缀越权 → 上游拒绝（401/403），不放行。

### 7.5 前端

- 统一前端请求层（http.ts）登录后持有 JWT；不自行构造身份头（三头仅由网关注入）。
- 前端经 `/auth/me` 读取身份上下文（含可见前缀集合/名下智能体列表），实现"我的智能体"切换与聚合视图（对应 §4.3 用户私有域前缀）。

## 8. 错误码与异常

| 错误码 | HTTP | 触发 | 行为 |
|--------|:----:|------|------|
| `AUTH_IDENTITY_INCOMPLETE`（新增，建议码 401013） | 401 | JWT 四维 claims 缺失/非法（第 1、2 跳） | 拒绝请求，返回统一错误格式 |
| `PERM_IDENTITY_FORBIDDEN`（新增，建议码 403014） | 403 | 前缀越权 / 上游数据隔离校验失败（第 2、3 跳） | 拒绝访问，不暴露越权数据存在性 |
| `SYS_UPSTREAM_ERROR`（沿用） | 502 | 上游不可达 | 沿用现有包装 |
| `AUTH_UNAUTHORIZED`（沿用） | 401 | 未认证 | 沿用现有包装 |

> 错误码登记需同步更新 `openbase/core/errors/codes.py` 与全局错误码表。

## 10. 隔离策略声明表（数据层级落点）

各系统/数据域声明数据在组织树上的层级落点，实现与过滤义务按 §7.4 执行：

| 系统/数据域 | scope 层级落点 | 访问方 | 典型前缀查询 |
|------------|---------------|--------|-------------|
| 画像系统-团队共享画像 | team 层 `{t}/{team}/` | 团队成员 + 绑定智能体 | `{t}/{team}/%` |
| 画像系统-用户私有画像 | user 层 `{t}/{team}/{user}/` | 本人 + 授权智能体 | `{t}/{team}/{user}/%` |
| 记忆系统-个人记忆 | user 层 | 本人 + 授权智能体 | `{t}/{team}/{user}/%` |
| 知识库-团队共享 | team 层 | 团队成员 | `{t}/{team}/%` |
| 知识库-智能体私有 | agent 层 `{t}/{team}/{user}/{agent}/` | 绑定智能体 + 拥有者 | `{t}/{team}/{user}/{agent}/` |
| 会话/工作区 | agent 层 | 绑定智能体 | 精确匹配 |
| 租户公共配置/字典 | tenant 层 `{t}/` | 租户全员 | `{t}/%` |

> 多智能体共用画像/知识库 → 数据落 team 层或 user 层（智能体是访问者）；智能体私有域 → agent 层。隔离与共享均由前缀规则表达，各系统不得另设过滤逻辑。

## 11. 兼容与迁移策略

1. **双写优先，后断旧头**：JWT 与头部在契约生效期同时承载新旧字段（`org_id` 与 `team_id`/`agent_id`/`X-Scope` 并存），全部系统切换完成后（v1.5 全量切换节点）再移除旧字段。顺序不可颠倒。
2. **统一发布窗口**：五仓（OpenBase + OpenLLM + OpenRAG + OpenMemory + DPS）同一窗口发布；无法同窗时按"先 OpenBase 双写 → 逐仓消费切换 → 最后移除旧头"执行。
3. **存量数据 scope 回填**：存量数据行按"当前 owner → 组织树定位"批量回填 scope 列（幂等迁移脚本），作为发布前置；无归属数据归入对应租户根节点并登记审计。
4. **回退**：发布后任一系统隔离断言失败 → 回退该仓至双写前版本（旧头仍被全链支持），不阻断其他系统。

## 12. 测试与验收

### 12.1 契约测试断言清单（强制，纳入 Step 4）

| 用例 ID | 断言 | 级别 |
|---------|------|:----:|
| TC-JWT-001 | 登录/刷新后 JWT 四维 claims（sub/tenant_id/team_id/agent_id）齐全；无绑定为 `-` 占位 | P0 |
| TC-JWT-002 | 无租户用户拒绝签发（不默认注入租户） | P0 |
| TC-HDR-001 | 每个 proxy 端点（memory/llm/rag）转发请求携带三头（X-Tenant-Id/X-User-Id/X-Scope），X-Scope 4 段定长且与身份一致 | P0 |
| TC-HDR-002 | 缺任一头 / 推导失败 → 401/403（fail-closed），不放行 | P0 |
| TC-HDR-003 | X-Org-ID 双写期与 X-Tenant-Id 同值；切换后不再注入 | P1 |
| TC-ISO-001 | 用户 U 前缀 `{t}/{team}/{user}/%` 可聚合名下全部智能体数据；不可见其他用户/智能体 | P0 |
| TC-ISO-002 | 团队前缀 `{t}/{team}/%` 只返回团队域数据；租户管理员 `{t}/%` 全量 | P0 |

- 跨仓库集成契约测试（登录 → 三头 → 各系统前缀隔离断言）作为发布门禁。
- 契约文件变更必须走版本流程（本文件修订历史），禁止静默修改。

## 16. 附录：字段速查表

| 维度 | JWT Claim | 透传头 | 组织树层级 | 占位 |
|------|-----------|--------|-----------|:----:|
| 租户 | `tenant_id` | `X-Tenant-Id` | 第 1 段 | 必选，禁止占位 |
| 团队 | `team_id` | 并入 `X-Scope` 第 2 段 | 第 2 段 | `-` |
| 用户 | `sub` | `X-User-Id` | 第 3 段 | 必选，禁止占位 |
| 智能体 | `agent_id` | 并入 `X-Scope` 第 4 段 | 第 4 段 | `-` |
| 组织（废弃） | `org_id` | `X-Org-ID` | - | 迁移期=tenant_id，v1.5 后移除 |

`X-Scope` 示例：`openbase/ops-team/u-1001/a-2001`；用户级数据 `openbase/ops-team/u-1001/-`；无团队用户 `openbase/-/u-1001/-`。
