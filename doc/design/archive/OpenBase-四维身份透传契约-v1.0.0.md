## 1. 契约目的与范围

### 1.1 背景与问题陈述

OpenBase 统一前端/调用方经代理链（memory-proxy / llm-proxy / rag-proxy）访问四系统时，四维身份（用户、租户、团队、智能体）的透传存在以下已核实缺陷：

| # | 缺陷 | 证据 |
|---|------|------|
| P1 | JWT 仅携带用户 + 租户（org_id 为租户别名），**无 team_id / agent_id** | `openbase/modules/auth/__init__.py` 登录签发 `extra={"org_id": tenant_value, "role": role}` |
| P2 | memory-proxy 注入 `X-Org-ID`（值=租户）与 `X-Tenant-ID` 同值，语义混用；缺 `X-Team-Id/X-Agent-Id` | `openbase/modules/proxy/memory_proxy.py` `_build_upstream_headers` |
| P3 | llm-proxy / rag-proxy **零身份注入**；rag-proxy 对应 OpenRAG 无认证，登录用户可访问全部知识库 | `openbase/modules/llm_proxy/__init__.py`、开发需求文档-v1.4.4 §3.2 |
| P4 | 四维身份头解析能力（R-369 `IdentityContext`）已实现但**仅接入审计模块**，未接入任何代理链 | `openbase/core/deps/auth.py` `get_identity_context` 调用方仅 `openbase/modules/audit` |
| P5 | 团队管理（R-376）、智能体管理（R-377）顺延 v1.5，四维身份源头无实体管理 | 版本迭代路线图 §2.5 |

本契约定义四维身份从"签发 → 透传 → 消费"全链路的强制规范，作为 v1.5（B4 四维身份上下文全链透传契约 + B2 数据层双维度隔离）的落地基线。

### 1.2 契约目标

| # | 目标 | 验收对应 |
|---|------|---------|
| G1 | 四维身份在链路每一跳**显式存在**（允许默认实体值），不允许字段缺失 | §5/§6/§7 强制规则 |
| G2 | 四头注入**单一实现点**（OpenBase 网关/ProxyBase），代理只透传不改写 | §7.3 |
| G3 | 四系统数据层强制按租户×智能体双维度过滤（消费方义务） | §9 适配矩阵 |
| G4 | 消除 X-Org-ID 语义混用，统一 X-Tenant-Id + X-Team-Id | §6.3 迁移 |
| G5 | 契约可由测试/CI 强制校验（缺头即失败） | §11 测试与验收 |

### 1.3 适用范围

- OpenBase 认证模块（JWT 签发/校验）、统一网关（/api/v1/proxy）、三个专用代理（memory/llm/rag）及未来 DPS 代理
- 统一前端 openbase-ui（请求层携带与消费身份上下文）
- 四个上游系统（OpenLLM v2.13.0 / OpenRAG v1.8.0 / OpenMemory v6.8.0 / DPS）

### 1.4 边界与排除项

| 排除项 | 说明 |
|--------|------|
| 团队/智能体管理 API 设计（R-376/R-377） | 属于实体管理需求，本契约只定义其在 JWT/头中的透传形态 |
| 各系统数据层隔离的数据库实现细节 | 本契约只定义"必须按 X-Tenant-Id/X-Agent-Id 过滤"的义务与验收，实现由各系统设计 |
| 服务级 API Key 通道（/api/v1/proxy 双通道） | Key 通道不携带用户身份，沿用现状（R-367），不在本契约扩展 |

## 2. 核心概念与术语

| 术语 | 定义 |
|------|------|
| 四维身份 | 用户（User）/ 租户（Tenant）/ 团队（Team）/ 智能体（Agent）四个身份维度 |
| 四头 | 透传头 `X-User-Id` / `X-Tenant-Id` / `X-Team-Id` / `X-Agent-Id` |
| 默认实体 | 用户未显式归属某维度时注入的默认值（见 §4.2），保证四维恒有显式值 |
| 全链透传 | 身份从 JWT 签发 → 网关/代理注入 → 上游消费三段链路，逐跳显式承载 |
| fail-closed | 身份上下文缺失时拒绝请求（403），而非放行 |
| 单一实现点 | 四头注入逻辑只存在于 OpenBase 网关/ProxyBase 一处，代理不得各自实现 |
| IdentityContext | R-369 已实现的四维身份解析数据结构（openbase/core/deps/auth.py） |

## 3. 契约总则（必选语义）

### 3.1 "四维必选"的定义

> **四维身份上下文在认证链路每一跳上必须显式存在。允许承载默认实体值（§4.2），不允许字段缺失、不允许语义漂移、不允许代理自创头。**

- "显式存在"：JWT payload 与透传头中四维字段必须出现，且可解析出确定值。
- "不允许字段缺失"：不得出现"该字段不存在"（如当前 JWT 无 team_id/agent_id 字段）。
- "不允许语义漂移"：同一维度在链路各跳含义一致（如 org 不得在代理处被当作 team 使用）。
- "不允许自创头"：除 §6.1 定义的透传头外，代理不得发明/改写身份头。

### 3.2 默认实体注入

用户未绑定团队/智能体时，由 OpenBase 签发层注入默认实体（模式：默认实体注入，非"可空放任"）。默认实体具备与真实实体相同的隔离语义（个人隔离域）。

### 3.3 强制失效原则

任一跳检测到四维缺失/非法 → 立即拒绝（fail-closed），不允许降级放行。静默降级视为契约违规。

## 4. 四维身份模型

### 4.1 四维定义

| 维度 | 标识字段 | 必选级别 | 语义 |
|------|---------|:-------:|------|
| 用户 | `user_id`（JWT `sub`） | 必选 | 登录用户，链路源头 |
| 租户 | `tenant_id` | 必选 | 数据隔离第一维度；签发时强制非空 |
| 团队 | `team_id` | 必选（显式） | 数据隔离第二维度；未绑定 → 默认团队 |
| 智能体 | `agent_id` | 必选（显式） | 数据隔离第三维度；未绑定 → 默认智能体 |

### 4.2 默认实体值域

| 维度 | 默认值 | 说明 |
|------|--------|------|
| 租户 | `openbase-default` | 沿用现有约定（memory_proxy 缺省 org 值） |
| 团队 | `openbase-default-team` | 用户个人默认团队（个人隔离域） |
| 智能体 | `openbase-default-agent` | 用户个人默认智能体（个人隔离域） |

> 默认值常量由 OpenBase 统一导出（如 `openbase/core/identity.py`），禁止各系统各自硬编码等价字符串。

### 4.3 值域与格式

- `user_id`：正整数或字符串，全链保持字符串形态传递（避免 int/str 类型漂移）。
- `tenant_id` / `team_id` / `agent_id`：非空字符串，`^[a-zA-Z0-9_-]{1,64}$`，禁止含 `/`、空格、控制字符（防头注入）。
- 四维在链路各跳的**值必须完全一致**（代理不改写、不映射）。

## 5. JWT 契约

### 5.1 Claims 规范

| Claim | 类型 | 必选 | 说明 |
|-------|------|:----:|------|
| `sub` | string | 必选 | 用户 ID（四维之"用户"） |
| `username` | string | 可选 | 用户名（冗余） |
| `tenant_id` | string | 必选 | 租户编码；签发时强制非空（无则注入 `openbase-default`） |
| `team_id` | string | 必选 | 团队编码；未绑定 → `openbase-default-team` |
| `agent_id` | string | 必选 | 智能体编码；未绑定 → `openbase-default-agent` |
| `role` | string | 可选 | 用户角色（RBAC） |
| `org_id` | string | 废弃 | 迁移期与 `tenant_id` 同值；v1.5 全量切换后从 JWT 移除 |
| `permissions` | array | 可选 | 权限点（沿用现状） |

### 5.2 签发规则（强制）

1. `create_access_token` 必须携带四维 claims（`sub`/`tenant_id`/`team_id`/`agent_id`），任何维度缺失即视为签发错误（拒绝签发并记录审计）。
2. `tenant_id` 从用户实体读取；用户无租户时注入默认租户，但**必须在签发审计中标记"默认租户"**。
3. `team_id`/`agent_id` 从用户绑定关系读取；未绑定注入默认实体。
4. 刷新（refresh）签发的 access token 必须与原始签发的四维一致（refresh token 需携带并回填四维）。

### 5.3 校验规则

- `decode_access_token` 后必须校验四维 claims 完整性；缺失即视为无效 token（拒绝服务）。
- 校验函数收敛为单一实现（如 `validate_identity_claims(payload) -> IdentityContext`），供 `get_current_user`、各代理复用。

### 5.4 兼容与废弃

| 阶段 | 动作 |
|------|------|
| 契约生效期（双写） | JWT 同时携带 `team_id`/`agent_id`（新）与 `org_id`（旧，值=tenant_id），保证存量消费方不破 |
| v1.5 全量切换后 | 从 JWT 移除 `org_id`；任何继续依赖 `org_id` 的调用方视为契约违规 |

## 6. HTTP 透传头契约

### 6.1 四头规范

| 头 | 必选 | 来源 | 说明 |
|----|:----:|------|------|
| `X-User-Id` | 必选 | JWT `sub` | 用户 ID |
| `X-Tenant-Id` | 必选 | JWT `tenant_id` | 租户 |
| `X-Team-Id` | 必选 | JWT `team_id` | 团队（含默认实体） |
| `X-Agent-Id` | 必选 | JWT `agent_id` | 智能体（含默认实体） |

### 6.2 注入规则

1. **单一实现点**：四头由 OpenBase 网关/ProxyBase 统一注入（基于 §5.3 校验后的 IdentityContext），三个代理（memory/llm/rag）及未来 DPS 代理**只透传不改写**。
2. 所有经 OpenBase 转发至上游的请求（含 `/api/v1/proxy/{system}/*` 与三个专用代理端点）必须携带四头。
3. 上游不可达/上游无认证系统（OpenRAG）在无认证期间：四头仍注入，隔离义务由 OpenBase 侧租户级白名单兜底（§9）。

### 6.3 废弃头迁移（X-Org-ID）

| 阶段 | 动作 |
|------|------|
| 现状 | memory-proxy 注入 `X-Org-ID`（值=tenant_id）——**语义混用缺陷** |
| 契约生效期（双写） | 同时注入 `X-Org-ID`（兼容，值=tenant_id）与 `X-Team-Id`（正确语义）；OpenMemory 侧按 §9 对齐 |
| v1.5 全量切换后 | 停止注入 `X-Org-ID`；上游仍消费 `X-Org-ID` 视为对接缺陷，由消费方跟进 |

## 7. 链路各跳强制规则

### 7.1 链路结构

```
统一前端/调用方（携带 JWT）
  → ① OpenBase 认证签发（四维 claims 全量签发，§5）
  → ② 网关/ProxyBase（IdentityContext 校验 + 四头统一注入，§6.2）
  → ③ 上游系统（强制校验四头 + 数据层租户×智能体过滤，§9）
```

### 7.2 第 1 跳：OpenBase 认证签发

- 义务：§5.2 签发规则、§5.3 校验规则。
- 强制校验：登录/刷新后 JWT 四维 claims 完整性测试（§11 TC-JWT-001）。

### 7.3 第 2 跳：网关/代理（唯一注入点）

- 义务：校验 JWT → 构造 IdentityContext → 注入四头 → 转发；缺四维 → 403（fail-closed）。
- 禁止：代理内自定义身份提取逻辑、改写/映射四头、选择性注入。
- 现有三代理改造范围：
  - memory-proxy：删除自研 `_extract_identity`/`_build_upstream_headers` 中的身份部分，改调统一注入器；补 `X-Team-Id/X-Agent-Id`；`X-Org-ID` 进入双写迁移。
  - llm-proxy：新增四头注入（当前零注入）。
  - rag-proxy：新增四头注入 + 租户级白名单（OpenRAG 无认证期间）。

### 7.4 第 3 跳：上游系统消费

- 义务：所有数据访问（列表/详情/写操作/检索）强制带 `tenant_id` + `agent_id` 过滤条件（对应 B2）；无过滤的查询视为 P0 缺陷。
- 校验：缺失四头时上游应拒绝（401/403）而非放行。

### 7.5 前端

- 统一前端请求层（http.ts）登录后持有 JWT；不自行构造四头（四头仅由网关注入）。
- 前端可在用户信息接口（/auth/me）读取四维上下文用于展示与切换（团队/智能体切换入口随 R-376/R-377 落地）。

## 8. 错误码与异常

| 错误码 | HTTP | 触发 | 行为 |
|--------|:----:|------|------|
| `AUTH_IDENTITY_INCOMPLETE`（新增，建议码 401013） | 401 | JWT 四维 claims 缺失/非法（第 1、2 跳） | 拒绝请求，返回统一错误格式 |
| `PERM_IDENTITY_FORBIDDEN`（新增，建议码 403014） | 403 | 上游数据隔离校验失败（第 3 跳） | 拒绝访问，不暴露越权数据存在性 |
| `SYS_UPSTREAM_ERROR`（沿用） | 502 | 上游不可达 | 沿用现有包装 |
| `AUTH_UNAUTHORIZED`（沿用） | 401 | 未认证 | 沿用现有包装 |

> 错误码登记需同步更新 `openbase/core/errors/codes.py` 与全局错误码表（TD-新增-008 模式）。

## 9. 各系统适配矩阵

| 系统 | 现状（已核实） | 目标（本契约） | 关键动作 |
|------|---------------|---------------|---------|
| OpenBase 认证/网关 | JWT 缺 team/agent；IdentityContext 仅接审计；代理各自实现身份逻辑 | 统一签发四维 + ProxyBase 单一注入 + fail-closed | JWT 四维签发、统一注入器、三代理改造 |
| OpenLLM | 主平台 API 不消费身份头（仅 EdgeRouter 层约定） | 消费四头并数据层过滤（tenant×agent） | 主 API 身份头消费（衔接对接完善任务书） |
| OpenRAG | 无认证、无身份消费（最大缺口） | M1 认证落地 + 消费四头 + 数据层过滤 | 认证落地前置为本契约 P0；落地前 OpenBase 租户白名单兜底 |
| OpenMemory | 消费 X-Org-ID/X-User-ID/X-Tenant-ID（缺 team/agent） | 对齐四头（X-Org-ID 迁移） | 消费 X-Team-Id/X-Agent-Id |
| DPS | 未对接 | 对接时直接按契约实现 | 无存量修正，按契约落地 |
| 统一前端 | 不构造身份头 | 保持不构造；支持四维上下文展示/切换 | /auth/me 返回四维上下文 |

## 10. 兼容与迁移策略

1. **双写优先，后断旧头**：JWT 与头部在契约生效期同时承载新旧字段（`org_id` 与 `team_id` 并存），全部系统切换完成后（v1.5 全量切换节点）再移除旧字段。顺序不可颠倒。
2. **统一发布窗口**：五仓（OpenBase + OpenLLM + OpenRAG + OpenMemory + DPS）同一窗口发布；无法同窗时按"先 OpenBase 双写 → 逐仓消费切换 → 最后移除旧头"执行。
3. **回退**：发布后任一系统隔离断言失败 → 回退该仓至双写前版本（旧头仍被全链支持），不阻断其他系统。
4. **默认实体数据初始化**：存量用户批量注入默认团队/智能体绑定的迁移脚本作为发布前置（数据迁移，幂等）。

### 11.1 契约测试断言清单（强制，纳入 Step 4）

| 用例 ID | 断言 | 级别 |

- 跨仓库集成契约测试（登录 → 四头 → 四系统隔离断言）作为发布门禁。
- 契约文件变更必须走版本流程（本文件修订历史），禁止静默修改。
