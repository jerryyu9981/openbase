## 2. 系统架构

### 2.1 总体架构（v1.4.6 目标态）

```
                        ┌──────────────────────────────────────┐
   前端 /system/logs ──▶│  网关（既有） /api/v1/logs/**         │
   （仅 log:read）       │  Depends(require_permission)          │
                        └──────────────┬───────────────────────┘
                                       ▼
                    ┌──────────────────────────────────────────┐
                    │  logs 模块（本版本新增）                   │
                    │  ┌────────────────────────────────────┐  │
                    │  │ Controller: router.py              │  │
                    │  │  /logs/search  /logs/facets        │  │
                    │  │  /logs/export                      │  │
                    │  └──────────────┬─────────────────────┘  │
                    │                 ▼                        │
                    │  ┌────────────────────────────────────┐  │
                    │  │ Service: LogQueryService           │  │
                    │  │  参数归一 / 分页 / facets 聚合 /    │  │
                    │  │  截断语义 / 导出编排                │  │
                    │  └──────────────┬─────────────────────┘  │
                    │                 ▼                        │
                    │  ┌────────────────────────────────────┐  │
                    │  │ Derivation: 分类派生（单点）        │  │
                    │  │  module / operation / result       │  │
                    │  └──────────────┬─────────────────────┘  │
                    │                 ▼                        │
                    │  ┌────────────────────────────────────┐  │
                    │  │ Repository: 适配器（可插拔）        │  │
                    │  │  L1FileAdapter    → jsonl 文件读取  │  │
                    │  │  AuditDbAdapter   → audit_logs SQL  │  │
                    │  │  TestRecordAdapter→ 测试记录服务    │  │
                    │  └────────────────────────────────────┘  │
                    └──────────────────────────────────────────┘
                                       │
              ┌────────────────────────┼────────────────────────┐
              ▼                        ▼                        ▼
   logs/openbase/                 audit_logs 表           测试记录服务
   openbase-YYYYMMDD.jsonl        （PG）                  （test-runs/records）
```

**核心架构原则：单一出口 + 适配器可插拔**。上层（Controller/Service）只认识统一 `LogEntry`；三源的形态差异被**完全封装在适配器内**；新增数据源只需新增一个适配器并注册枚举，不改上层。

### 2.2 模块挂载设计

| 项 | 设计 |
|----|------|
| 新增模块 | `openbase/modules/logs/`（**独立新模块**，不与 `modules/audit` 混装） |
| 模块文件 | `__init__.py`（导出 router）、`router.py`（Controller）、`service.py`、`derivation.py`、`repository.py`、`schemas.py` |
| 挂载方式 | 在 `openbase/demo_app.py` 以既有模块挂载模式注册 `logs` router（前缀 `/api/v1`） |
| **不选**扩展 `modules/audit` | 原因：`audit` 承载**中间件 + 写入链路**（请求路径内的日志与落库），把数百行的多源查询层塞进去会让"写链路"与"查链路"职责混淆，且不利于 Step 3 独立测试 |
| 权限依赖 | 沿用既有模式 `from openbase.modules.auth.rbac import require_permission`；三端点统一 `dependencies=[Depends(require_permission("log:read"))]`（对标 `testing` 模块的 `require_permission("test:record")`） |
| 配置 | 新增 settings 项：`log_query_max_days`（默认 2）、`log_query_max_lines`（默认 200000）、`log_export_max_rows`（默认 10000）、`log_query_default_window_hours`（默认 24）；**不新增依赖** |
| **决策点（Step 3 施工前确认）**（v1.1.0） | ① **`gateway` 模块注册身份处置**：保留其模块注册项（仅前端导航归位）**或**一并迁移至平台管理；需评估对 `GET /api/v1/modules` 消费侧与既有 `permission` 的影响（需求评估报告 §6#2）；② **`logs/{svc}` svc 名 ↔ `module` 名映射表**的落点（建议置于 `derivation.py` 同文件，与既有 module 派生规则同址，避免两处分叉）；③ **模块注册表持久化形态**（DB 表 vs 配置驱动）→ 决定 `PATCH /api/v1/modules/{id}` 可写或降级只读（ADR-146-07） |

### 2.3 适配器契约（Repository 层）

三适配器实现**同一协议**，使 Service 无需分支判断源形态：

| 方法 | 语义 |
|------|------|
| `fetch(filters, *, limit, offset) -> tuple[list[LogEntry], int, bool]` | 返回「条目列表 / 命中总数 / 是否因上限截断」；**排序与过滤在适配器内完成**（时间倒序 + 稳定次序） |
| `facets(filters) -> dict[str, Counter]` | 返回**同一 filters 条件下**的 module / operation / result / operator 计数（与 `fetch` 同口径，供 AC-146-02-4 互证） |

| 适配器 | 数据源 | 关键实现要点 |
|--------|--------|--------------|
| `L1FileAdapter` | `logs/openbase/openbase-YYYYMMDD.jsonl` | ① 由时间窗推导需扫描的**日分片列表（倒序）**；② **文件名白名单**校验（`openbase-\d{8}\.jsonl`）+ 目录规范化，拒 `..`/绝对路径；③ 逐行 JSON 解析（坏行跳过并计数，不中断）；④ 累计行数触顶即提前终止并置 `truncated=True` |
| `AuditDbAdapter` | `audit_logs` 表 | ① SQLAlchemy **参数化查询**（禁止字符串拼接）；② 时间/`action`/状态码等可在 SQL 层下推的过滤优先下推；③ `detail` JSON 内的 `case_id`/`run_id`/`step_id` 用 JSON 取值表达式；④ `COUNT` 与分页查询分两步（避免全量拉取） |
| `TestRecordAdapter` | 测试记录服务 | ① **只读调用**既有服务（不复制其内存结构）；② 以 `run_id`/`case_id`/`step_id` 为主检索键；③ `result` 直接取记录字段（无需状态码派生） |
| **`RepoLogAdapter`**（v1.1.0 新增，第四类源） | **四仓采集日志文件** `logs/{svc}/{svc}-YYYYMMDD.jsonl`（dps / openllm / openmemory / openrag） | ① **按 service 目录选择文件**（`logs/{svc}/`），沿用 L1 同一套**文件名白名单 + 日分片倒序 + 提前终止 + 上限截断**逻辑；② **JSONL 解析优先 + 纯文本回退**（兼容未完成结构化的仓）；③ **`logs/{svc}` 的 svc 名 ↔ `module` 名的映射须显式化**（常量映射表：`dps`→`dps`、`openrag`→`rag`、`openmemory`→`memory`、`openllm`→`llm`），**禁止硬编码散落**；④ 字段映射：四仓 JSONL 最小集 9 字段 → `LogEntry` 18 字段（缺失落 `null`/`unknown`）；⑤ 服务端统一脱敏（**不得因新源放宽**）；⑥ 坏行跳过并计数（沿用 L1 口径） |

## 3. 关键架构决策（ADR）

### ADR-146-01 统一查询接口 + 适配器层（vs 三接口并置 / ETL 归一入库）

| 项 | 内容 |
|----|------|
| 上下文 | 三源存储形态与字段完全不同；需求要求**跨源同一套分类与检索语义** |
| 备选方案 | ① **统一接口 + 适配器层**（选中）；② 三接口并置 + 前端多页签；③ ETL 归一入库后只查一处 |
| 决策 | 采用 ① |
| 理由 | ② 会把分类/派生/分页逻辑复制三份，且检索条件无法跨源组合；③ 引入同步组件与一致性风险，且与"日志写入不阻塞主请求"约束冲突、违背 C-1 不变量 T6-1（不做自动清理/轮转）的克制口径 |
| 已知后果与风险 | 需定义统一 `LogEntry` 与派生规则（一次性成本）；L1 无索引，需扫描上限与 `truncated` 语义（已作为设计约束登记） |

### ADR-146-02 分类派生规则集中在后端单点实现

| 项 | 内容 |
|----|------|
| 上下文 | L1 记录**无** `module`/`operation` 字段，只能由 `path`+`method` 派生；若各源各自派生会出现口径分裂 |
| 备选方案 | ① 后端 `derivation.py` 单点实现，三适配器复用（选中）；② 各适配器自行派生；③ 前端派生 |
| 决策 | 采用 ① |
| 理由 | 满足 AC-146-02-1（未知值落 `other`/`unknown` 且不丢记录）与 AC-146-02-4（facets 与列表同口径）；前端派生会导致分页计数与筛选不一致 |
| 已知后果与风险 | 派生规则演进需回归三源；已在 Step 3 以单元测试锁定枚举映射表 |

### ADR-146-03 L1 扫描采用「分片倒序 + 提前终止 + 显式截断」

| 项 | 内容 |
|----|------|
| 上下文 | jsonl 无索引；大时间窗全量扫描不可接受（§7 要求 P99<2s） |
| 备选方案 | ① 倒序分片扫描 + 命中足量提前终止 + 上限截断（选中）；② 全量扫描后分页（简单但慢）；③ 建索引/入库（超范围） |
| 决策 | 采用 ①；默认上限：**≤2 个日分片 / ≤200,000 行**（settings 可配）；触顶返回 `truncated=True` |
| 理由 | 用"已知且显式的不完整"换取可预测响应时间；**禁止静默截断**（AC-146-04-3） |
| 已知后果与风险 | 大时间窗检索结果可能不完整；UI 必须显著提示（已在 UI 设计 §4 落地）；彻底解决需索引化（需求排除项 #7，另立需求） |

### ADR-146-04 导出留痕独立于查询（写 `audit_logs(action=log.export)`）

| 项 | 内容 |
|----|------|
| 上下文 | 决议 2 要求导出可审计；但需求 §5.3 又声明三源"只读" |
| 备选方案 | ① 导出时追加一条 `audit_logs` 留痕行（选中）；② 不留痕；③ 写 L1 结构化日志 |
| 决策 | 采用 ①：`action="log.export"`，`detail` 记录 `{actor, filters 摘要, row_count, format}`；**不记录导出内容本身** |
| 理由 | 满足合规可审计；写入量与既有审计写入同源同路径（复用 `AuditLog` 模型），不新增表 |
| 已知后果与风险 | 引入一条**写路径**，故 §5.3 规则需精确表述为"只读，唯一例外是导出留痕"（需求文档已同步修正）；留痕失败不得导致导出失败（降级：`WARN` 但不阻断导出） |

### ADR-146-05 目录边界治理：平台/全局页迁出模块目录

| 项 | 内容 |
|----|------|
| 上下文 | 实测发现 `/system/roles`、`/system/org`、`/system/workspaces`、`/system/config`、`/system/audit`、`/system/edgerouter`、`/system/docs`、`/system/billing` 的组件文件**全部位于 `modules/openllm/pages/`**，由静态路由 import —— 模块边界与功能归属不一致，打包上全局页与 openllm 同 chunk，**模块可插拔性被侵蚀** |
| 备选方案 | ① **迁出至 `src/pages/platform/**`**（选中）；② 保持原位仅改注释/文档说明；③ 改为动态模块（把全局功能做成第 6 个模块） |
| 决策 | 采用 ①：平台/全局类页面组件迁至 **`src/pages/platform/**`**，使**模块目录只含本模块特色页** |
| 理由 | ② 不解决问题（chunk 仍耦合、审计仍无法从目录判断归属）；③ 会让"平台管理"变成可被停用的模块，与 AC-146-10-2「平台管理区不受单一模块启停影响」直接冲突 |
| 已知后果与风险 | **大规模文件移动属破坏性变更**（迁出 15 项组件 + 上收 14 项）→ 以 ADR-146-08 的**重定向映射表 + 引用检索存证 + 特色页零删减硬门禁**闭环；构建产物需核验 openllm chunk 不再含全局页 |

### ADR-146-06 四仓日志采用「单源承载 + module 维度」而非「四仓各一源」

| 项 | 内容 |
|----|------|
| 上下文 | 四仓日志形态同质（同为采集到的日志文件、同一最小字段集），差异仅在 service 归属 |
| 备选方案 | ① **单源 `repo_log` + `module` 维度区分**（选中）；② 四仓各一 `source`（`dps_log`/`rag_log`/…）；③ 四仓并入既有 `l1_file` 源 |
| 决策 | 采用 ①：新增 **`source=repo_log`**，以 `module`（`dps`/`rag`/`memory`/`llm`）区分四仓 |
| 理由 | ② 会使 `source` 枚举随仓数线性膨胀，且前端"按模块筛选"与"按源筛选"维度重叠、口径易分裂；③ 会把"本仓自身日志"与"被代理方日志"混为一源，破坏 `l1_file` 的既有语义（只读 `logs/openbase/`） |
| 已知后果与风险 | 需**显式化 `logs/{svc}` ↔ `module` 映射**（防硬编码散落）；单源内需按 `module` 分区扫描（先定 module 再定 svc 目录），扫描上限按**目标 svc 目录**独立计算而非四仓合计（避免单仓体量大时挤占其它仓的扫描预算） |

### ADR-146-07 模块注册表写路径：`module:manage` + 留痕 + 不强制热生效

| 项 | 内容 |
|----|------|
| 上下文 | 模块开关管理页（BL-146-15）是「平台配置与密钥」域的实质内容，但模块注册表**当前只有只读消费侧**（`GET /api/v1/modules`），且**持久化形态待核实**（DB 表 vs 配置驱动） |
| 备选方案 | ① **新增写接口 `PATCH /api/v1/modules/{id}` + 权限码 `module:manage` + `audit_logs(action=module.switch)` 留痕，标注"下次登录/刷新生效"**（选中）；② 仅做只读展示页（降级）；③ 做写接口并实现热生效（前端动态更新模块路由） |
| 决策 | 采用 ①；**若 Step 3 核实后确认注册表为纯配置驱动且改动成本过高，则按 ② 降级为只读展示，并在交付说明显式标注**（需求 §4.15「依赖」已预留该降级路径） |
| 理由 | ③ 会引入"模块启停影响运行中会话"的复杂状态（未授权范围，且与本版本"治理 IA、不动模块装配语义"的边界冲突）；② 单独不可接受（这正是目前 ⑥ 域名不副实的根因） |
| 已知后果与风险 | 引入**一条新的写路径 + 可能的最小持久化**（登记为风险 11）；权限码 `module:manage` 需幂等授权（与 `log:read` 同口径）；写操作**必须留痕**（操作人 / 模块 `id` / 前后状态） |

### ADR-146-08 前端 IA 重构采用「重定向映射表 + 权限三处一致」收敛

| 项 | 内容 |
|----|------|
| 上下文 | IA 重构涉及上收 14 项、迁出 15 项组件的大规模移动（ADR-146-05），且顶层由扁平 `/system/*` 改为**三分 + 平台管理四域**；既有书签、走查脚本、E2E 与文档引用均指向旧路径 |
| 备选方案 | ① **全量旧→新重定向映射表 + 权限码/菜单/路由守卫三处一致**（选中）；② 直接替换路径（旧路径 404）；③ 保留新旧双入口长期并存 |
| 决策 | 采用 ①：①**平台管理统一前缀 `/platform/**`**（`/system/**` 保留为重定向来源）；② 产出**全量重定向映射表**，旧路径**禁止 404**；③ **权限码 ↔ 菜单可见性 ↔ 路由守卫三处一致**（同一权限码驱动三处，禁止各写一套） |
| 理由 | ② 会打断既有走查脚本与文档引用（不可接受的可用性回归）；③ 长期双入口会造成"同一功能两个入口、两套命名"，与本次"消除系统性功能重复"的目标相悖 |
| 已知后果与风险 | 映射表是**破坏性变更的安全网**，必须**在迁移前全量产出并逐条验证**；`meta.permission` 需与后端权限码同名（否则会出现"菜单可见但接口 403"的割裂）；E2E 须覆盖旧路径遍历抽样 + 双角色菜单可见性 + 深链 + `console.warn=0` |

## 4. 数据模型设计

**本版本不新增任何表、不新增文件、不做迁移**。`LogEntry` 是**查询视图实体**（非持久化实体）。

| 项 | 设计 |
|----|------|
| 视图实体 | `LogEntry`（**18 字段**，见《API接口设计文档-v1.4.6》§2） |
| 持久化实体 | 沿用 `audit_logs`（既有表，零迁移）；L1 沿用既有 jsonl 落盘口径；测试记录沿用既有内存+落库口径 |
| 新增枚举取值 | `audit_logs.action` 新增取值 **`log.export`** 与 **`module.switch`**（v1.1.0 增补，无 schema 变更，`action` 为 `varchar`） |
| 索引需求 | **不新增索引**（`audit_logs` 既有查询按 `created_at`/`action`/`request_id` 过滤；如需索引化另立需求） |
| 数据字典 | 复用《OpenBase-数据库设计文档-v1.2.0》既有定义；本版本无字段增删 |

## 5. API 设计摘要

详见《OpenBase-API接口设计文档-v1.4.6》。三端点：

| 端点 | 方法 | 权限 | 用途 |
|------|------|------|------|
| `/api/v1/logs/search` | GET | `log:read` | 统一检索（分类 + 关键字 + 时间窗 + 三元组 + 分页）；`source` 枚举含 `l1_file`/`audit_db`/`test_record`/**`repo_log`** |
| `/api/v1/logs/facets` | GET | `log:read` | 分类计数（左侧导航） |
| `/api/v1/logs/export` | GET | `log:read` | CSV / JSON 导出（≤10000 条）+ 留痕 |
| **`/api/v1/modules/{id}`** | **PATCH** | **`module:manage`** | **（v1.1.0 新增）模块启用/停用；写 `audit_logs(action=module.switch)` 留痕；标注"下次登录/刷新生效"** |

## 6. 安全设计

| 项 | 设计 |
|----|------|
| 认证 | 复用既有 JWT 门禁，不新增认证方式 |
| 授权 | 三端点统一 `Depends(require_permission("log:read"))`；前端路由 `meta.permission='log:read'` → 双校验（AC-146-07-1） |
| 可见范围 | 持 `log:read` 者**跨租户可见**（决议 1）→ 适配器**不施加 tenant 过滤**；该口径在代码注释与测试中显式标注，避免后续误加过滤 |
| 脱敏 | 服务端复用既有统一脱敏（C-18 `mask_sensitive`）处理 `summary`/`detail`；**前端不承担脱敏** |
| 路径穿越防护 | L1 适配器**三重校验**：① 时间窗推导出的文件名由代码生成（非用户输入拼接）；② 白名单正则 `^openbase-\d{8}\.jsonl$`；③ `Path.resolve()` 后确认仍在 `logs/openbase/` 之下（AC-146-07-3） |
| 注入防护 | 关键字/分类/操作人全部走 Pydantic 模型 + **枚举白名单**，异常值直接 400；SQL 全参数化 |
| 检索词不落盘 | 查询关键字不写入 L1 与 `audit_logs`（AC-146-03-3） |
| 导出合规 | 仅管理员可用；导出留痕（ADR-146-04）；导出内容同样脱敏（AC-146-06-3） |
| **模块开关权限**（v1.1.0） | 新权限码 **`module:manage`**（仅管理员）；无权限 403；页面/入口不可见（AC-146-15-2）；写操作**强制留痕** `module.switch`（AC-146-15-3） |
| **四仓日志脱敏**（v1.1.0） | 四仓日志经 `RepoLogAdapter` 统一脱敏，**不得因新源放宽口径**；四仓 JSONL 中的 token 等敏感键 → `[MASKED]`（AC-146-19-3） |

## 8. 一致性约束（对既有架构）

| 既有面 | 本版本影响 |
|--------|-----------|
| 写入链路（审计中间件 / `AuditPersistQueue`） | **不改动**；仅新增一条由导出触发的 `audit_logs` 写入（经既有 `AuditLog` 模型） |
| `audit_logs` 表结构 | **零迁移**（仅新增 `action` 取值 `log.export`） |
| `/audit/records` 内存端点 | **不改动**（`/memory/api-gateway` 继续可用） |
| 身份头 / 信任链（P2-1、K03） | **不改动** |
| 前端既有页面 | 仅新增 1 页 + 1 条重定向；`/system/audit` 由 mock 改为重定向（BL-146-09） |
| T6-1 不变量（日志不自动清理） | 未新增任何清理/轮转路径 |
| 分层与错误码 | 严格遵循 `AGENTS.md`（Controller/Service/Repository + `{code,message,detail,request_id}`） |
| **前端 IA 重构**（v1.1.0） | 顶层由扁平 `/system/*` 改为**三分 + 平台管理四域**；平台管理统一前缀 **`/platform/**`**，`/system/**` 保留为重定向来源（禁 404）；权限码 ↔ 菜单 ↔ 守卫三处一致（ADR-146-08） |
| **模块目录边界**（v1.1.0） | 平台/全局页组件迁出 `modules/openllm/pages/` → `src/pages/platform/**`（ADR-146-05）；**四模块特色页零删减**（硬门禁）；openllm chunk 不得再含全局页 |
| **`gateway` 模块归位**（v1.1.0） | `gateway` 从「业务模块」区迁入平台管理「可观测与审计」域（服务发现与聚合编排）；**其模块注册身份处置**（保留注册项仅前端归位 / 一并迁移）在 §2.2 决策点登记，Step 3 施工前确认 |
| **四仓边界**（v1.1.0） | R-383 阶段**不改四仓**；R-384 阶段**必须改动四仓**（各自评审与发布）；本仓**不代改**他仓代码（VC-014） |
