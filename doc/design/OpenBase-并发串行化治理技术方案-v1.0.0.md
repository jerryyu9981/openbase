## 1. 问题定义（可测量）

### 1.1 现象（实测，非推断）

| 口径 | `achieved_rps` | P50 | P95 | P99 | 错误 |
|------|:---:|:---:|:---:|:---:|:---:|
| **单飞**（并发 1，不限节流，`P-6` 同端点） | **6.501 req/s** | — | — | — | 0 |
| **并发 8**（`peak_in_flight = 8`，不限节流） | **9.317 req/s** | 918.8 ms | 17,145.8 ms | 21,901.0 ms | 1 × `RemoteProtocolError` |
| 并发 8 **对照单发** | — | **6.4×** 劣化 | **约 119×** 劣化 | — | — |

**并发收益比：8× 并发仅换得 1.43× 吞吐（达真并行理想值约 52 req/s 的 17.9%）。**

> 首轮（v1.3.0，未关闭 SQLAlchemy `echo`）为 `achieved_rps = 1.578`、P95 17,145.8 ms；关闭 `echo` 后（现测）提升至 9.317 req/s，**但并发收益比仍为 1.43× → 串行化主体依然存在**（债表「未偿还」判定成立）。

### 1.2 受影响指标与判定口径

| 指标 | 单飞档 | 并发 8 档 | 说明 |
|------|:------:|:---------:|------|
| `P-6` 回执查询（队列 473 行 = **S1**） | ❌ 未达标（P50 132.1 ms，S1 内即超） | ❌ 未达标 | 双口径一致 |
| `P-8` `traces` 查询（863 行 = **S2**） | ❌ 未达标（P95 741.7 ms） | ❌ 未达标 | 双口径一致 |
| `P-9` 消息查询（3 行 = **S1**） | ✅ 达标 | ❌ 未达标 | 双口径分歧点 |
| `P-11` 吞吐 | 不判（口径规定由并发档判） | ✅ 9.317 req/s ≥ 基线 1.578×80% | **名义达标**，但收益比严重不足（见 §1.1） |
| `P-12` 并发档错误率 | — | ❌ 未达标（首轮 13.3% / 6.7%，`DT-148-016` 修复后归零复测中） | 连接层亦受牵连 |
| **`P-4` 首包本仓额外开销** | ✅ 达标（P95 40.0 ms） | ❌ 未达标（**P95 189.0 ms**） | 与上列**同源** |

**判定口径**：结论须注明**口径（单飞 / 并发 8）**与**数据规模档位**（§1.1.2a：S1 ≤500 行 / S2 501–5,000 行 / S3 5,001–50,000 行），**基线对比须同档位**。

## 2. 根因分析（逐处定位，含证据）

### 2.1 三类同步 I/O 落在 `async def` 请求路径内

| # | 位置 | 事实（源码/配置） | 为何阻塞事件循环 |
|:-:|------|------------------|------------------|
| **R-1** | `app/services/writeback_queue.py`（`WritebackStore`） | `async def enqueue()` / `async def list_rows()` 为 **async 外壳**，内核实为同步 `sqlite3.connect()`（`_connect()`，WAL + `busy_timeout=5000`），且**整体包在 `async with self._lock` 全局 asyncio 锁内** | ① 阻塞 sqlite3 调用**直接在事件循环线程执行**；② 全局 asyncio 锁使**三路回写与回执查询彼此串行**；③ 锁内做同步 I/O → 持锁时间＝I/O 时间，放大串行效应 |
| **R-2** | `app/api/openllm_gateway.py` 各 `async def` 端点内的**同步 SQLAlchemy 会话**（`app/db/session.py`：`scoped_session(sessionmaker(bind=engine))`，PG `postgresql://…@192.168.0.151:5432/nuct`，`pool_size=10`） | 请求路径直接调用同步 Session（查询/写入） | 同步 DB 往返（含网络 RTT）阻塞事件循环；**同一 worker 内所有协程被迫排队** |
| **R-3** | `app/db/session.py:20/31` `echo=settings.DEBUG`；`backend/.env` `DEBUG=True` | 每请求输出**全量 SQL 日志**（同步 I/O） | 发现 #11：单飞档被拖慢至约 **2.3 s/请求**；关闭后单飞 6.501 req/s |
| **R-4** | 语义缓存 `app/core/semantic_cache.py`（`import sqlite3`） | 同类同步 sqlite 访问（**待逐处核对是否命中请求路径**） | 与 R-1 同类，需在实施设计阶段逐处确认 |
| **R-5** | 部署形态 | 启动命令 `python -m uvicorn main:app --host 127.0.0.1 --port 8041`，**无 `--workers`** | 单 worker ⇒ 上述阻塞**无任何并行退化空间**（多进程可掩盖，但不治本，见 §4 方案 C 约束） |

### 2.2 机理（一句话）

> **`async def` 端点 → 同步 sqlite3 / 同步 SQLAlchemy → 阻塞唯一事件循环线程 → 协程无法并发推进**；再叠加 `WritebackStore` 的**全局 asyncio 锁内做同步 I/O**，使「并发 8」退化为「串行 8 + 每次付 I/O 代价」→ **吞吐不升、尾延迟按并发数线性放大**（P95 劣化 119× 与排队效应一致）。

### 2.3 已排除项（避免重复归因）

* **`echo` 日志非唯一根因**：关闭后并发收益比仍为 1.43×（仅相对首轮改善吞吐绝对值）→ 属**叠加项**（债表已如此登记）。
* **并发未生效的可能已排除**：驱动侧实测 `peak_in_flight = 8`（并发确实打满）。
* **限流污染已排除**：压测使用提高限流的专用实例（`RATE_LIMIT_PER_SECOND`），未节流档 `achieved_rps = 9.317` 非限流上限所致。
* **未做分离实验（如实登记）**：`DT-148-015` / `DT-148-016` 修复对吞吐的贡献未与 `echo` 关闭做对照分离 → §4 阶段 1 复测时应补一次「控制变量」测量。

## 4. 备选方案与选型（ADR）

### 4.1 备选方案

| 方案 | 做法 | 优点 | 缺点 / 风险 |
|:----:|------|------|-------------|
| **A 线程卸载**（对症，最小改动） | 把请求路径内的**阻塞 I/O 段**移入线程池：sqlite3 段用 `run_in_threadpool` / `anyio.to_thread.run_sync`；`WritebackStore` 的 `asyncio.Lock` 改 `threading.Lock`（锁不得跨线程使用）；同步 SQLAlchemy 段按「每线程自建 Session」卸载 | 改动局部、风险低、可增量、**不引入新依赖**；直接消除事件循环阻塞 | 线程池默认上限（anyio 40）在超高并发下仍受限；需逐处确保 **Session/连接不跨线程复用**（既有 `DetachedInstanceError` 类问题须协同处理） |
| **B DB 访问异步化**（治本，大改） | PG 侧改 `asyncpg` + `AsyncSession`（`sqlalchemy.ext.asyncio`）；SQLite 侧改 `aiosqlite` 或迁移为 PG 表 | 根治；无双线程模型切换开销 | 改动面大（依赖、事务边界、迁移、错误语义、契约核验），回归成本高；SQLite→PG 迁移涉及数据与运维 |
| **C 多 worker 部署**（容量级） | `uvicorn --workers N`（或 gunicorn + uvicorn worker） | 吞吐可近似线性扩展；**代码零改动** | **不解决单 worker 内串行化**（尾延迟仍劣化）；**关键约束：跨进程共享态语义改变**——`_get_model_router()`（`@lru_cache` 单例）、`_profile_failure_until`（画像失败冷却）、`_pending_stream_writebacks`（回写 drain）、`WritebackStore` 的 asyncio 锁均**按进程独立** → 熔断计数/冷却/压测口径失真，须先定义跨进程语义（外置存储或接受「每进程独立」） |

### 4.2 推荐路线：**分阶段 A → C →（视需要）B**

| 阶段 | 内容 | 目的 |
|:----:|------|------|
| **阶段 1（推荐先做）** | **方案 A**：R-1 / R-2 / R-4 的阻塞段线程卸载 + **运行态口径固化**（压测实例一律 `DEBUG=false`） | 对症消除事件循环阻塞，**以最小改动取得可测量的收益比提升** |
| **阶段 2** | **方案 C**：多 worker，并**先定义跨进程共享态语义**（§4.1 约束） | 在单 worker 已不串行的前提下提升吞吐上限；避免用多 worker 掩盖问题 |
| **阶段 3（可选）** | **方案 B**：DB 访问异步化 | 仅当阶段 1+2 仍无法满足目标（或需进一步压降尾延迟）时启动 |

**选型理由**：阶段 1 直击 §2.2 机理且可独立验收；阶段 2 的收益依赖阶段 1 已消除串行化（否则只是把串行复制到 N 个进程）；阶段 3 成本最高、仅在证据表明必要时投入（遵循「先测量再优化、一次一维」原则）。

## 5. 阶段 1 实施设计（推荐方案细则）

### 5.1 阻塞段清单（须逐处核对后定稿）

| 序 | 目标位置 | 改造模式 | 校验点 |
|:-:|----------|----------|--------|
| 1 | `WritebackStore._connect` / `enqueue` / `list_rows`（及 `max_seq` 等） | 阻塞 sqlite 段整体移入线程池；**`asyncio.Lock` → `threading.Lock`**；连接仍在函数内创建/关闭（**不跨线程复用**） | 幂等语义不变；三路回执序号不重不乱；锁语义（互斥范围）不变 |
| 2 | `openllm_gateway` 内同步 SQLAlchemy 调用点（会话/模型/计费/回执聚合等） | 计数并分类（读/写/队列），逐类卸载；**每线程自建 Session，用完即关**；读取仅取**标量**（与 `DT-148-016` 修复方向一致，防 `DetachedInstanceError`） | 事务边界不变；`5001` 类错误不回归；错误响应契约不变 |
| 3 | `semantic_cache`（待核对） | 同上（若命中请求路径） | 缓存命中/失效语义不变 |
| 4 | 运行时开关 | 压测/联调实例 `DEBUG=false`（**纳入压测环境规范**，发现 #10/#11） | 启动日志实证生效 |

### 5.2 一致性约束（不得违反）

1. **不得跨线程复用 ORM 实例/连接**（`SessionLocal` 为 `scoped_session`，跨线程共享需显式解除）。
2. **锁的层次与范围保持不变**（仅替换实现类型，不改变互斥语义）。
3. **不改变对外契约**：两路径一致性、错误码/错误体、越权隔离（`DEF-BE-148-007`）、回执归属过滤（`user_id` fail-closed）均须保持。
4. **回写语义不回退**：`CR-148-020` 的「后台派发 + 回执另行持久化」（含 `_dispatch` 占位与有限等待）行为不变。

### 5.3 TDD 护栏（先写后改）

| 护栏 | 断言 |
|------|------|
| **源码契约** | ① `WritebackStore` 内**不得**出现「阻塞 sqlite 调用直接在协程中执行」的形态（可由「阻塞段必须包在卸载入口内」锁定）；② 卸载段内**不得**使用 `asyncio.Lock` |
| **行为：并发不串行** | 以 2 个并发任务打同一卸载点，断言 **总耗时 ≈ 单次耗时**（而非 2×）—— 直接锁定「并发不再退化为串行」 |
| **行为：锁语义保持** | 幂等入队（同 `request_id`+`target` 不重复）、`seq` 连号不回退 |
| **不回归** | `5001` / `DetachedInstanceError` 类用例保持通过；回执查询归属过滤保持 |

## 7. 验收标准（可判定，**阈值待立项确认**）

### 7.1 功能与回归（阻断性）

| 项 | 判据 |
|----|------|
| 权威口径全量回归 | `pytest tests/unit`（**不加** `--confcutdir`）→ **failed 不高于 31**、`error = 0` |
| 静态质量 | 改动文件**改动行零告警**（既有欠账不计） |
| 契约与隔离 | 定向用例全绿（两路径一致性 / 错误契约 / 越权 / 回执归属） |

### 7.2 性能（并发 8 档为判定档；单飞档为**防退化**档）

| 指标 | 判据 | 备注（建议值，**须确认**） |
|------|------|---------------------------|
| 并发收益比 | `achieved_rps(并发8) / achieved_rps(单飞)` | 现 **1.43×** → 建议 **≥3×**（保守）；**目标值建议立项时定**（理想上限 8×，考虑远端 PG RTT 与 sqlite 锁，建议不要直接设 8×） |
| `P-6` / `P-8` | 同档位、同规模（S1/S2）下达 §1.1.2 目标 | 现均未达标，须**由「未达标」转「达标」或出改进幅度** |
| `P-9` | 并发 8 档达 P50 ≤100 / P95 ≤300 / P99 ≤500 ms | 单飞已达标（S1） |
| `P-4` | 并发 8 档 P95 ≤100 ms | 现 189.0 ms |
| `P-12` | 并发档错误率 0（H 类除外） | 连接层（keep-alive / 超时）须一并无错 |
| 单飞档 | 各指标**不得劣化**（同档位对比，容差 ≤10%） | 防「为并发牺牲单飞」 |

### 7.3 回退条件

若阶段 1 后并发收益比 **< 2×** 或 `P-6`/`P-8` 无实质改善 → **回步骤 3 重新定位**（考虑阶段 3 或判定「远端 PG RTT 为环境性上限」并据此重设目标）。
