## 2. 业务目标

| 目标 ID | 业务目标 | 用户目标 | 成功指标 |
|---------|----------|----------|----------|
| G1 | 回写闭环成立（P3 回写） | 用户的记忆 / 画像 / 知识库随会话推进被自动更新，无需人工维护 | 三路回写（记忆 / 知识库 / 画像）在**同步与流式两条路径**均生效；回写回执（受理状态 / 投递序号 / 被丢弃项）覆盖率 **100%** |
| G2 | 回写不丢（P3；**硬判据**） | 服务重启后用户历史回写不丢失 | **重启后回写丢失数 = 0**（F-08 回归用例） |
| G3 | 会话轴成立（P1 精准） | 多轮对话中「他刚才说的那个呢」这类指代能被正确理解 | 多轮指代类问题能正确利用会话历史；四类素材（画像 / 记忆 / 知识库 / 历史）注入覆盖率 **100%**（不可用须留降级记录） |
| G4 | 结构前置就绪 | 同步 / 流式两种调用方式行为一致，不再有隐性分叉 | 同步与流式两路径同输入行为一致（路由结果、注入片段集合、缓存命中一致） |
| G5 | 基线可测（**条件目标**，受 D3 约束） | 上下文的精准与省 token 可被量化证伪 | 无条件部分：工装就绪（第零段交付）；F-02 修正后日期化模型名窗口取值正确（`gpt-4o-2024-08-06` → 128000 / `o200k_base`）。**条件部分：B0 与 B1 两份基线报告的产出以 D3 确认为前提**；D3 暂缓确认期间本目标记为「条件未满足」，不据此判定版本失败 |

> 目标 1~4 为无条件目标；目标 5 部分条件化（D3 暂缓确认，见 §11 风险）。

## 3. 现状核实结论（Step 1 关键输入，代码实测）

> 本节为写需求前对现状的**实测核对**，依据派单 §1 / §3 与统一方案 §3 的代码实测结论，用于锁定范围与排除项，避免需求落在不存在的接口上。

| # | 核实项 | 实测结论 | 证据（代码位置） |
|:-:|--------|----------|------------------|
| 1 | 编排引擎是否存在 | **已存在且完整**：组件路由器、auto/explicit 编排器、Jinja2 组装器、回写回调；**缺的是**会话轴接入、预算裁剪、双路径收敛与回写接线，非新建编排层 | `edgerouter/orchestration/` |
| 2 | 会话轴是否接入 | **缺位**（F-07）：`_normalize_request` 只取**最后一条 user 消息**，多轮对话在 `/chat` 上完全没有上下文 | `openllm_gateway.py:995-1009` |
| 3 | 回写幂等键现状 | **有缺陷**（F-08，已实测复现）：`session_id=user_id` + `seq` 取模块级进程内计数器；重启后计数器归零、`INSERT OR IGNORE` 命中 → **重启前 N 次回写全部静默丢弃**（实测 N=3，桩 handler 应执行 4 次实际 1 次） | `openllm_gateway.py:620-626`；证据 `doc/test/evidence/f08/f08-seq-restart-repro-20260921.txt` |
| 4 | 三路回写接线现状 | **一条未生效**（F-09）：`_build_writeback_callback` 只返回 memory + rag 两个回调，**无 profile 路**；流式路径 `_run_stream_components` **完全无回写** | `openllm_gateway.py:629-664`、`:667-` |
| 5 | 是否有 token 计量 | **无**（F-11）：编排链路无 token 计量、无注入片段记录、无回执；「注入了多少 token / 注入了哪些片段」的分子分母都不存在 | 统一方案 §3.4 |
| 6 | 模型窗口前缀匹配 | **有缺陷**（F-02）：`MODEL_CONTEXT_LIMITS` 按插入顺序 `startswith` 匹配，日期化模型名 `gpt-4o-2024-08-06` 落到 `gpt-4o` 前的通用项 → 窗口 **8192 / `cl100k_base`**（实际 128000 / `o200k_base`，**低估 15.6 倍**） | `context_manager.py:43-86`、`:176-178`、`:198-200` |
| 7 | 双路径是否分叉 | **分叉**（F-01）：流式路径自建 Prompt 组装副本、绕过 `PipelineExecutor`；`model="auto"` 与 `mode="auto"` 在流式路径均被绕过 | 统一方案 §3.5 |
| 8 | 既有队列库数据 | `backend/data/writeback.db` 已有数据：**实测 26 行 / 8 会话**（含 `s1` seq 1..4、`s2` seq 1..8），幂等键改会话维度须保留并加迁移说明 | 派单 §2.4 |
| 9 | 独立 API 路径是否已修复 | **已修复**（他仓 R-003）：`api/writeback.py:376-378` 已按 `max_seq+1`；**编排路径未同步，本次即补齐漏改** | `api/writeback.py:376-378` |
| 10 | 网关是否需要改动 | **无需改动**：`llm_chat(payload: dict[str, Any])` 原样转发请求体，新增字段直接透传 | `llm_proxy/__init__.py:355-366` |
| 11 | 前端会话标识现状 | 发消息只提交 `{ model, messages }`，**不带会话标识**；会话记账将退化为按用户 | `openbase-ui/src/core/api/llm.ts:101`、`:113` |
| 12 | 流式回写可行性 | **待核实**（R3）：流式响应结束点是否有可靠的「最终回答全文」可供回写，当前 `_run_stream_components` 不接收回写参数 | 派单 §2.5（开工前回填） |

**结论**：本版本改动**主体在 OpenLLM 仓**（编排与预算能力、会话轴、回写、幂等键、窗口匹配）；**openbase-ui 仓**配合提交会话标识（另行派单）；**本仓（OpenBase）不实施 OpenLLM 侧代码改动**（`VC-014`），仅承担 BL-148-08 文档口径整合与 BL-148-07 报告框架。

## 4. 功能需求

> 需求编号 RT-148-01~08 与 Backlog BL-148-01~08 一一对应；验收标准 AC-148-xx-y 见 §11。

### 4.1 RT-148-01 第零段：基线工装（仅观测，不改行为）（P0）

新增一套**只观测**的计量工装，为三条原则提供可证伪的基线数据。

| 项 | 要求 |
|----|------|
| 工装 1 Prompt 组成计量 | 记录最终 prompt 总 token 与六段分项 token（`system` / `profile` / `memory` / `rag` / `history` / `query`）；分母口径：四类素材（画像 / 记忆 / 知识库 / 历史）注入片段之和，**不含** `query` 与输出 `max_tokens` 预留 |
| 工装 2 检索快照 | 记录 memory 与 rag 返回**条目数、各条 `score`、实际进入 prompt 的条目与 token**（支撑 WCR 判定） |
| 工装 3 回执落库 | 上述两项 + `request_id` / 会话标识 / 模型 / 时间戳，写入 `routing_trace` 或独立表，**可批量导出** |
| 工装 4 归因 A | 引用检测：由片段抽取关键 n-gram / 关键词集合，回答命中即视为使用；随每次调用计算，零额外模型调用 |
| 工装 5 归因 B 工具 | 抽样（每轮 ≥30 条）调用判定模型，逐片段输出 used / unused / uncertain；**固定判定 prompt、固定判定模型与版本**；片段**去标识并打乱顺序**；判定模型优先**不与被评模型同源** |
| 工装 6 固定集与评分表 | golden set（7 场景矩阵，每场景 ≥5 条，合计 ≥35 条，含 2 组负例）+ 四维 1~5 分评分量表 + 记录模板 |
| 工装 7 汇总脚本 | 从回执导出指标，生成基线报告（含方法 / 样本量 / 漏检率区间） |
| **硬约束** | 工装 1~7 **一律不得含裁剪、改写或截断逻辑**；本段**不改变任何对话输出**（同输入前后输出一致）；禁止记录令牌 / 密码 / 密钥 / 完整请求体 |
| 落点 | OpenLLM 仓编排链路（`orchestrator` / `assembler` / `runner`）+ `routing_trace` 或独立表 + `openllm_gateway.py`（归因 A 随调用计算，不改响应语义） |
| 验收 | AC-148-01-1~5 |

### 4.2 RT-148-02 F-02 窗口上限前缀匹配修正（P0）

修正模型窗口前缀匹配缺陷，保证计量与后续预算裁剪取值的正确性。

| 项 | 要求 |
|----|------|
| 修正点 | `MODEL_CONTEXT_LIMITS` 匹配由「插入顺序 `startswith`」改为**最长键优先匹配**或**显式别名表** |
| 预期结果 | `gpt-4o-2024-08-06` → **128000 / `o200k_base`**（现值 8192 / `cl100k_base`）；`gpt-4-turbo-2024-04-09`、`gpt-4-32k-0314` 用例通过 |
| 用例 | 补日期化模型名回归用例（上述三个模型名） |
| 定位 | 计量可信前置：不修则 WCR 与预算利用率同时失真（窗口低估 15.6 倍） |
| 落点 | `context_manager.py:43-86`、`:176-178`、`:198-200` |
| 验收 | AC-148-02-1~2 |

### 4.3 RT-148-03 前置零：双路径收敛（R-397）（P0）

消除同步与流式两路径的分叉，为后续各项改动建立单一实现面。

| 项 | 要求 |
|----|------|
| 共用步骤抽取 | 把「组件执行 → 上下文格式化 → 预算 → 组装」抽为**共用步骤**，供 `/chat` 与 `/chat/stream` 共用；消除流式路径自建的 Prompt 组装副本 |
| 流式路径补齐 | 补齐回写与语义缓存语义，或按 §2.5 前置核实结论**显式声明不提供并写入契约**（不得静默缺失） |
| 行为对齐 | `model="auto"` 须走 5 因子路由与 fallback；`mode="auto"` 须经 `ComponentRouter` 决策（现流式路径两者均绕过） |
| 测试 | 同一输入分别打两路径，断言行为一致（含路由结果、注入片段集合、缓存命中） |
| 落点 | `openllm_gateway.py`（同步路径与 `_run_stream_components`） |
| 验收 | AC-148-03-1~3 |

### 4.4 RT-148-04 会话轴接入（R-396）（P0）

让多轮会话的历史进入上下文，闭合「精准」的会话维度。

| 项 | 要求 |
|----|------|
| 历史纳入 | `_normalize_request` 停止只取最后一条 user 消息；把历史**按窗口纳入上下文**（`ContextManager.get_context_window` 或等价的按 `max_tokens` 截取） |
| 请求契约 | `OpenLLMChatRequest` 新增**会话标识字段（可选）**；缺省时退化为按用户记账（保持既有调用方兼容） |
| 组装位置 | 历史作为第五类素材参与组装；`assembler` 现有严格顺序为 System + 画像 + 记忆 + 知识库 + Query，**历史插入位置须明确**（设计阶段定稿，不得破坏既有顺序语义） |
| 会话落库 | `conversations.py` 会话消息落库与检索对齐新的会话标识口径 |
| 跨仓 | openbase-ui 仓提交会话标识（D2，另行派单）；前端缺省不提交时会话记账退化为按用户 |
| 验收 | AC-148-04-1~4 |

### 4.5 RT-148-05 三路回写接齐（R-398）（P0）

让记忆 / 知识库 / 画像三路回写在同步与流式两条路径均生效，并提供回执。

| 项 | 要求 |
|----|------|
| profile 路纳入 | `_build_writeback_callback` **新增 profile 路回调**（现只返回 memory + rag 两个） |
| 流式回写补齐 | `_run_stream_components` **补齐流式路径的 memory / rag / profile 回写**（现完全无回写）；触发点与聚合方式按前置核实 §2.5 结论实现 |
| 回写回执 | 三路各自的 `accepted` / `duplicated` / `failed`、投递 `seq`、被丢弃项标识，**可查**（第一批起必需） |
| 失败隔离 | 回写通道失败**不得影响主链路**（沿用既有异步队列与指数退避 ≤3 次） |
| 降级 | 组件不可用一律降级不报错（沿用既有 `ComponentUnavailableError` 与 degraded 标记语义） |
| 验收 | AC-148-05-1~4 |

### 4.6 RT-148-06 回写幂等键修正（F-08）（P0；**硬判据**）

修复重启后回写静默丢失的 P1 数据完整性缺陷。

| 项 | 要求 |
|----|------|
| 幂等键 | `(session_id, seq, target)`，其中 **`session_id` 必须为真实会话标识**，禁用 `identity.user_id` 顶替 |
| `seq` 取值 | **必须取持久化来源**：`WritebackStore.max_seq(session_id) + 1`；**禁止**使用模块级进程内计数器（`openllm_gateway.py:620-626`） |
| 硬判据 | **重启后回写丢失数 = 0**（复用 F-08 复现用例形态：跨进程受控重启前后对比） |
| 历史兼容 | 既有行保留 + 迁移说明（实测 26 行 / 8 会话），**不做破坏性删除** |
| 禁止 | 不得仅靠 `recover_pending` 自愈（它只重跑已入库行，不回填计数器） |
| 验收 | AC-148-06-1~4 |

### 4.7 RT-148-07 B0 / B1 基线测量与报告（P0（条件），受 D3 约束）

产出基线测量报告，作为「更精准」「更省 token」的证伪依据。

| 项 | 要求 |
|----|------|
| 无条件部分 | 工装就绪（RT-148-01 交付）；F-02 修正生效（RT-148-02 交付） |
| **条件部分（D3 确认后）** | **B0 基线报告**：第零段后、前置零前测量，严格只观测；含方法 / 样本量 / 漏检率区间；B0 本身测不出改善，报告以相邻点位差值为主、绝对值为辅 |
| | **B1 基线报告**：第一批后测量；证明 P1（会话轴）与 P3（回写接齐）在 B0→B1 的差值 |
| 判定方法 | 三层递进：A 引用检测（每次调用，主指标，**只能纵向对比不得作绝对值解读**）+ B LLM 归因（抽样 ≥30 条，校准漏检率，判定模型不与被评模型同源）+ C 消融（一次性 10~15 条，效度检验） |
| WCR 口径 | `硬浪费片段 token / 注入上下文 token`；须同时给出软占用率与必要占用率（三者之和 = 1），不得只给单值 |
| 人工走测 | 7 场景矩阵（含 2 组负例）、每场景 ≥5 条共 ≥35 条、四维 1~5 分量表、固定 `temperature=0`、盲评 + ≥20% 样本间隔 ≥24h 复评算自一致性；记录评分人 / 日期 / 模型版本 / 问题集版本 |
| 判定规则 | token 降但评分明显降 → **判失败**；评分升但 token 显著升 → 须预算利用率仍有余量且超窗率 = 0；指标未变须说明原因；数据不足记「不可判定」须重测 |
| **D3 未确认期间** | 本条**挂起**并保留测量入口；不得以「无基线数据」规避其余硬判据（重启后回写丢失数 = 0、两路径行为一致） |
| 验收 | AC-148-07-1~3 |

## 5. 非功能需求

| 类别 | 指标 / 要求 | 判定方式 | 关联 |
|------|-------------|----------|:----:|
| 性能 | 回写对主链路时延影响 = **0**（异步不阻塞，沿用既有队列与退避） | 两路径各跑一次会话对比时延 | G1 |
| 性能 | 第零段**不改变任何对话输出**（同输入前后输出一致） | 同一输入分别打第零段前 / 后对比 | G5 |
| 可用性 | 回写通道失败**不得影响主链路**；组件不可用降级不报错 | 注入组件故障跑会话 | G1 |
