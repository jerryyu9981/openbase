## 3. 移交要点（Step 2 设计输入）

### 3.1 日志中心线（R-382，后端为主）

| 要点 | 说明 |
|------|------|
| 架构模式 | 「统一查询接口 + 适配器层」：单一 `GET /api/v1/logs/search` 按 `source` 路由三适配器 + 统一 `LogEntry`（可插拔） |
| 分层约束 | Controller（校验）/ Service（编排 + 分页）/ Repository（文件读取、SQL、服务调用）；禁止跨层与路由内拼 SQL |
| 数据契约 | `LogEntry` 18 字段 + 三源映射 + 派生规则（module/operation/result **后端单点**） |
| 接口契约 | `/logs/search`、`/logs/facets`、`/logs/export`；统一错误体 + 错误码 PARAM_400/AUTH_401/PERM_403/SYS_503/SYS_500 |
| 权限 | `log:read`（仅管理员）；**跨租户可见**；路径白名单（防穿越）；服务端脱敏；关键字不落日志 |
| 性能 | P99<2s；扫描上限 ≤2 分片 / 200,000 行；`truncated` 显式；`page_size`≤100；导出≤10,000 |
| 可观测性 | 三端点自身请求落 L1；导出写 `audit_logs(action=log.export)` |

### 3.2 布局重构线（R-383，前端为主）

| 要点 | 说明 |
|------|------|
| **顶层三分** | 仪表盘 / 业务模块（画像·知识库·记忆·模型 平行）/ 平台管理（四域）/ 个人与帮助；`gateway` 迁出业务模块区 |
| **平台管理四域** | 身份与权限 / 平台配置与密钥 / 可观测与审计 / 开发者资源 |
| **功能归属矩阵** | 需求 §10.6（**唯一事实源**）；Step 2 须补齐**路径列**并处理 `GenericPage` 多路由复用情形 |
| **上收判定口径** | 业务专有 → 留模块；跨模块通用（治理/观测/配置/身份/密钥/用量）→ 上收 |
| **模块瘦身** | 上收 **14 项**（13 页 + `gateway` 模块）；**特色页零删减**（硬门禁） |
| **目录边界治理** | 全局页迁出 `modules/openllm/pages/`（**15 项组件**）→ 目标如 `src/pages/platform/**`；openllm chunk 不得含全局页 |
| **路由兼容** | 全量旧→新**重定向映射表**，旧路径**禁 404**；统一前缀（`/platform/**` vs 保留 `/system/**`）Step 2 定案 |
| **权限一致性** | 权限码 ↔ 菜单可见性 ↔ 路由守卫**三处一致** |
| **模块开关管理页** | `/platform/config/modules`：列表 + 启停 + 权限码 `module:manage` + `audit_logs(action=module.switch)` 留痕 + 后端状态写接口 |
| **必须遵守** | **不改视觉规范**；**不改四模块业务逻辑**（只搬迁与入口归位）；不做移动端专项 |

### 3.4 四仓日志接入线（R-384，跨仓为主）

| 要点 | 说明 |
|------|------|
| **前置核实（设计前必办）** | ① OpenMemory **实际启动路径**（`basicConfig` 仅在 `main()`）；② OpenRAG **两套日志栈统一方案**（`observability/logging.py` vs `config/logging.py`）；③ 四仓受信来源判定口径对齐 |
| **跨仓契约（8 项，强制）** | 见需求 **§11.1**：头名与语义 / 字段名统一 `request_id`（禁 `correlation_id` 别名）/ 兜底 `-` 禁 `KeyError` / 输出流不变 / 统一 JSONL / 禁记敏感 / 各自评审发布 / 受信判定沿用既有实现 |
| **两条既有通道（无需新建）** | 出站 `X-Request-Id` 装配（`protocol_headers/inject.py`）+ 编排器重定向采集（C-6）—— 均已就绪 |
| **新增数据源** | `source=repo_log`（**单源承载四仓**，以 `module` 区分 `dps`/`rag`/`memory`/`llm`）；`RepoLogAdapter` 须实现**既有适配器协议**（`fetch`/`facets`）→ 不破坏既有三适配器架构 |
| **字段映射** | 四仓 JSONL 最小集 9 字段 → `LogEntry` 18 字段**显式映射表**；缺失落 `null`/`unknown`；**`logs/{svc}/` 的 svc 名 ↔ module 名映射须显式化**（避免硬编码；需求评估报告 §6#8） |
| **采集改造** | 按日切分 + `.jsonl` 命名（`{svc}-YYYYMMDD.jsonl`）；**不删历史、重启不覆盖**；以复用既有"分片倒序扫描 + 上限截断"逻辑 |
| **安全** | 四仓日志**服务端统一脱敏**且「不得因新源放宽」；沿用 `log:read`；关键字不落日志 |
| **降级与覆盖声明** | JSONL 优先 + **纯文本回退**；未覆盖范围**必须在交付说明逐仓列明**（禁止静默降级；需求评估报告 §6#11） |
| **跨仓验收凭据** | 各仓评审记录 + 提交凭据 + 各仓回归通过报告（需求评估报告 §6#7） |

## 4. 风险提示（带入 Step 2）

| # | 风险 | 设计应对方向 |
|:-:|------|--------------|
| 1 | **大规模文件移动（上收 14 + 迁出 15）属破坏性变更** | 先出**全量重定向映射表**；删除/移动前**全局引用检索并存证**；分域分批；每批 E2E；特色页零删减核对 |
| 2 | 归属判定与既有引用/文档路径不一致 | 矩阵补齐路径列；Step 4 走查清单按新 IA 复核并登记差异 |
| 3 | 模块开关页引入新写路径与可能的最小持久化 | Step 2 先核实持久化形态；必要时降级只读；留痕与权限同步设计 |
| 4 | L1 无索引 → 大时间窗不完整 | 分片倒序 + 提前终止 + 上限 + `truncated` 提示（禁静默截断） |
| 5 | 导出含个人信息 | 仅管理员 + 脱敏 + 留痕（留痕失败不阻断导出） |
| 6 | 三源口径不一致 | 派生规则单点 + `/facets` 与列表同源同条件互证 |
| 7 | IA 重构导致深链/console 告警回归 | 保留旧路径可达 + 启动预热装载（既有机制）+ E2E `console.warn=0` |
| **8** | **跨仓排期不可控**（R-384 最大单点风险，高/高）：四仓改动属他仓流程，本仓无法单方推进 | **不阻断** R-382/R-383 部分；按两批推进（批 A D-6 / 批 B 结构化+适配器）；`repo_log` 保留纯文本回退；**交付说明逐仓列明覆盖状态**；Phase 6 开工前完成 3 项前置核实 |
| **9** | **OpenRAG 两套日志栈未统一** → 存在"改了非生效那套"的实现风险 | 设计与施工前**先出栈统一决策记录**，再改格式（需求评估报告 §6#10） |
| **10** | 四仓日志量仅 dev 实测（≈1.82 MB/1~2 天），**生产量级未知** | Step 2 复核扫描上限与 `truncated` 参数；Step 4 补容量抽样（含 `truncated` 触发验证）（需求评估报告 §6#9） |
