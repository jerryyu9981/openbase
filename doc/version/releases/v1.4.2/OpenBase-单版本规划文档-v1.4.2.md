## 1. 版本概述

### 1.1 版本定位

| 项 | 内容 |
|----|------|
| 版本主题 | 四维身份管理基础（租户/用户）+ OpenMemory 对接（两 Phase） |
| 版本类型 | 能力补足版本（增量） |
| 基线 | v1.4.1（Step 5 已部署发布，全流程闭环） |
| 周期 | 3 周（Phase 1 四维管理基础 1.5 周 + Phase 2 OpenMemory 对接 1.5 周） |

### 1.2 背景与问题

| # | 问题 |
|---|------|
| ① | UAT 走查发现（2026-08-29）：R-369 已实现四维身份头承载（X-User-Id/X-Tenant-Id/X-Team-Id/X-Agent-Id 解析+透传），但**租户/用户/团队/智能体均无真实管理 API 与管理界面** |
| ② | 前端租户管理页（SystemTenants.vue）、组织/团队/用户页（OrgTeamsUsersView.vue）为占位 mock 数据，无法进行真实管理操作 |
| ③ | 后端仅 tenant 模块 context/quota 端点 + org 模块 departments CRUD；auth 模块无用户管理；无 agent 模块 |
| ④ | 用户决策"先登记到 v1.4.2 版本"（VC-008） |
| ⑤ | 用户明确"四系统挂起只是暂时挂起，需逐个对接，先对接 OpenMemory"（2026-08-29，上传《OpenMemory-对接使用指南-v6.8.0.md》）。OpenMemory 双层认证（X-API-Key + JWT{sub,org_id,role}）的 JWT 由 OpenBase 签发，**需用户/租户/角色体系前置**（VC-010） |

### 1.3 版本目标

| 目标 ID | 目标 | 验收指标 |
|---------|------|---------|
| G1 | 租户管理可用 | 租户 CRUD API + 管理界面（创建/编辑/停用/配额/列表），替换前端 mock |
| G2 | 用户管理可用 | 用户 CRUD API + 管理界面（创建/启停/角色分配/列表），替换前端 mock |
| G3 | OpenMemory 服务就绪 | OpenMemory v6.8.0 部署启动（端口 8020），健康检查通过，Qdrant/Neo4j/Redis/PG 依赖可用 |
| G4 | OpenMemory 对接闭环 | OpenBase 统一认证 → OpenMemory 记忆真实读写（remember/recall/forget/list），前端 2 页 mock 替换真实 API |
| G5 | 四维管理闭环 | 租户/用户管理数据可被四维身份头（R-369）引用，审计记录关联正确 |

## 3. 范围

### 3.1 包含范围（两 Phase）

**Phase 1：四维管理基础（1.5 周）** —— 提供用户/租户体系，作为 JWT 签发前提

| # | 需求 ID | 需求名称 | 优先级 |
|---|---------|---------|:---:|
| 1 | R-374 | 租户管理（Tenant CRUD API + 管理界面：创建/编辑/停用/配额/列表） | P1 |
| 2 | R-375 | 用户管理（User CRUD API + 管理界面：创建/启停/角色分配/列表） | P1 |

**Phase 2：OpenMemory 对接（1.5 周）** —— 双系统真实联通

| # | 需求 ID | 需求名称 | 优先级 |
|---|---------|---------|:---:|
| 3 | R-378 | OpenMemory 对接（启动服务 8020 + X-API-Key/JWT 双层认证共享 + proxy 转发适配 + 前端 2 页真实化 + 双系统联调） | P1 |

### 3.2 不包含范围（顺延/后续）

| # | 项 | 原因 |
|---|-----|------|
| 1 | R-376 团队管理（Team CRUD + 部门树继承 + 成员管理 + 授权） | 顺延 v1.5（VC-010）：OpenMemory 对接纳入后周期受限；授权深度留 v1.5 B3 完整实现 |
| 2 | R-377 智能体管理（Agent CRUD + 界面） | 顺延 v1.5（VC-010）：智能体业务场景未成熟，不阻塞 OpenMemory 对接 |
| 3 | 智能体×租户双维度隔离落地四系统数据层 | 依赖四系统数据层改造，v1.5+ |
| 4 | 四维身份上下文全链透传契约（四系统消费配合） | 依赖四系统接口配合，v1.5 |
| 5 | 四系统底座化回灌（B1）/可观测增强（B5）/Vault（B6）/虚拟 Key（B7） | 依赖四系统/基础设施，v1.5+ |

## 4. 优先级排序

| 优先级 | 需求 | 依据 |
|:---:|------|------|
| P1 | R-374 租户管理 | 多租户是 OpenBase 核心能力，租户 CRUD 缺失阻塞租户域管理；同时是 OpenMemory JWT org_id 签发前提（价值高/成本中） |
| P1 | R-375 用户管理 | 用户是四维第一维，认证/审计/授权均依赖用户实体管理；同时是 OpenMemory JWT sub/role 签发前提（价值高/成本中） |
| P1 | R-378 OpenMemory 对接 | 用户明确"逐个系统对接，先对接 OpenMemory"；双层认证打通后记忆功能真实可用，验证统一认证体系价值（价值高/成本中） |

## 6. 关键依赖与风险

| 类型 | 项 | 级别 | 应对 |
|------|-----|:---:|------|
| 依赖 | v1.4.1 完成（Step 5 部署） | P1 | 已发布，v1.4.1 全流程闭环 |
| 依赖 | OpenMemory v6.8.0 项目本机可启动（docker-compose/进程） | P1 | 项目位于 D:\Trae CN\myproject\Dev\OpenMemory；需改 API 端口 8000→8020 避免与 OpenBase 冲突 |
| 依赖 | OpenMemory 基础设施（Qdrant 6333/Neo4j 7687/Redis 6380/PG 5432）可用 | P1 | .env.shared-infra 已配置共享基础设施 |
| 依赖 | JWT 签名密钥与 OpenMemory 服务端配置一致 | P1 | OpenBase auth 签发 JWT 与 OpenMemory 校验端共享密钥配置（环境变量） |
| 风险 | 租户 schema 隔离与现有内存 QuotaManager 衔接 | P2 | 租户 CRUD 与配额管理器解耦，schema 隔离保持现状 |
| 风险 | 用户表扩展（角色关联/启停状态）影响既有登录链路 | P2 | 向后兼容迁移，登录/me 不动 |
| 风险 | OpenMemory 端口 8000 与 OpenBase 冲突 | P1 | OpenMemory 部署改端口 8020（部署配置覆盖，不动 OpenBase） |
| 风险 | OpenMemory 鉴权默认强制启用（API Key + JWT 双层） | P1 | OpenBase proxy 持有 X-API-Key + 统一签发 JWT，前端不接触密钥 |
