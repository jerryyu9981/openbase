## 1. 版本概述

### 1.1 版本定位

| 项 | 内容 |
|----|------|
| 版本主题 | **日志中心：分类查看与检索**（平台可观测性工具补齐）＋ **统一前端功能布局重构**（前端 IA 治理，VC-013）＋ **四仓日志接入**（日志域收官，VC-014）—— 按用户裁决"**把日志相关功能调整都放到一个版本里**"，**日志域全部工作集中于本版本** |
| 版本类型 | 增量版本（v1.4.x 线；**不并入**已规划的 v1.5「四系统统一集成测试 + 平台治理」） |
| 基线 | v1.4.5（Step 5 已闭环） |
| 周期 | **约 7.5 周**（原 2 周 → VC-013 后 4.5 周 → **VC-014 追加约 3 周**：D-6 四仓接线 + 四仓 JSONL 结构化 + 四仓日志适配器 + 端到端联调） |
| 范围登记 | R-382 + **R-383** + **R-384**（候选需求池 §1.12）+ VC-012 + **VC-013** + **VC-014**（版本范围变更总记录） |
| 回溯声明 | VC-013 触发 **Step 1→Step 2 回溯**：需求基线 / 追溯矩阵 / 前端类设计文档（UI·前端架构·系统架构·原型·设计评审）/ 覆盖率核对 / Stage1·Stage2 审计结论均需**升版重出**；VC-014 追加 **Step 1 第三轮补充**（R-384 → RT-146-16~20 / AC）与日志中心适配器**设计增补** |
| **跨仓声明** | **R-384 含跨仓依赖**：D-6 需在 **DPS / OpenLLM / OpenMemory / OpenRAG** 四仓各自评审与发布（4 仓 / 7 文件 / +38~+67 行；**协议先决：不改四仓代码的边界不再成立**）。据 VC-014：**本版本收口将绑定四仓排期**（登记风险 12，P1）；缓解措施：按 BL-146-16/17 两批推进、四仓改动以《D-6 四仓 request_id 日志接线改动说明》为施工依据、跨仓依赖纳入版本依赖清单 |

### 1.2 背景与问题

| # | 问题 |
|---|------|
| ① | S7「人工端到端测试日志落盘」流已落地三源日志（L1 结构化文件 / `audit_logs` 审计库 / 测试记录），但**无统一查看入口** —— 运维与测试只能靠脚本（`test_log_aggregate.py` / `test_log_analyze.py`）或直接读文件 |
| ② | 全仓 `api_router` 上仅有 `/audit/records` 一个端点，且数据源是 **内存环形缓冲 5000 条 / 进程重启即清空**，不具备检索能力 |
| ③ | 前端侧栏"审计日志"页（`/system/audit`）为**纯 mock**（`const mockLogs`），存在**误导风险** |
| ④ | 用户诉求：需要"**按使用习惯分类查看与检索**" —— 即能按业务模块 / 操作类型 / 结果 / 操作人快速收窄，并能按关键字 + 时间窗定位到具体请求 |
| ⑤ | 版本归属需澄清：路线图 §「v1.5 — 四系统统一集成测试 + 平台治理」已被占用，本功能为独立平台工具，宜单列增量版本 |
| ⑥ | **（VC-013 追加）统一前端功能布局失衡**：① **全局性功能"寄居"模块目录**——`/system/roles`、`/system/org`、`/system/workspaces`、`/system/config`、`/system/audit`、`/system/edgerouter`、`/system/docs`、`/system/billing` 等全局页的组件文件**全部位于 `modules/openllm/pages/`**，由静态路由直接 import → 模块边界与功能归属不一致、打包上全局页与 openllm 同 chunk、模块可插拔性被侵蚀；② **系统性能力四模块各造一套**（`openllm` 单模块 36 路由/33 菜单项即含"个人设置/API 密钥/用量/监控/成本/预算/告警/路由熔断"等系统性功能；`memory` 另有 `Admin`/`MemoryMonitorView`/`ApiGateway`；`portrait` 另有 `DpsMonitorView`/`DpsPermissionView`/`DpsApiManageView`/`DpsRateLimitView`；`knowledge` 另有 `Settings`/`Users`）→ 同类功能命名与入口口径不一致；③ 顶层 `/system/*` **扁平 11 项无分组**；④ 用户诉求："按统一系统的功能布局调整优化，不打破 dps/memory/rag/llm 四模块特色，把全局性和系统性功能统一起来" |

### 1.3 版本目标

| 目标 ID | 目标 | 验收指标 |
|---------|------|---------|
| G1 | 日志查询入口统一 | 单页覆盖 L1 / `audit_logs` / 测试记录三源且可切换（RT-146-01/08） |
| G2 | 分类贴合使用习惯 | 四维分类（模块 / 操作类型 / 结果 / 操作人）可点选过滤 + 计数（RT-146-02） |
| G3 | 检索可定位 | 关键字 + 多条件 + 时间窗 + 分页 + 测试三元组全部可用（RT-146-03/04/05） |
| G4 | 结果可导出留证 | CSV/JSON 导出可用、≤10000 条、导出行为留痕（RT-146-06） |
| G5 | 权限与脱敏合规 | `log:read` 生效、管理员跨租户、敏感字段 0 明文（RT-146-07） |
| **G6** | **统一前端功能布局重构**（VC-013） | 顶层导航**三分**（仪表盘/业务模块/平台管理）落地；平台管理**四域**二级分组可用；**「页面 → 目标域」归属矩阵 0 遗漏**且经人工确认；四模块**特色页零删减**；旧路径**无 404**（RT-146-10~15） |
| **G7** | **四仓日志接入**（VC-014） | 四仓日志**携带 `request_id`** 且与网关一致（可串联）；四仓日志**结构化（JSONL）**；OpenBase 日志中心**可检索四仓日志**（新增 `repo_log` 数据源）；端到端串联验收通过（RT-146-16~20） |

## 4. 版本风险清单

| # | 风险 | 概率 | 影响 | 应对 |
|:-:|------|:----:|:----:|------|
| 1 | L1 为逐行 JSON 文件、**无索引**，大时间窗扫描可能拖慢响应 | 中 | 中 | 强制扫描上限（≤2 个日分片 / ≤200,000 行）+ `truncated` 显式提示 + P99<2s 验收；必要时后置索引化（另立需求） |
| 2 | 导出含操作人与 IP，个人信息合规风险 | 中 | 中 | 仅 `log:read`（管理员）可导出 + 服务端脱敏 + **导出留痕** `audit_logs(action=log.export)` |
| 3 | L1 文件路径读取可能被穿越利用 | 低 | 高 | 文件名白名单 `openbase-YYYYMMDD.jsonl` + 目录限定，禁拼接用户输入 |
| 4 | 三源字段口径不一致导致分类/统计失真 | 中 | 中 | 统一 `LogEntry` + 派生规则集中在后端；`/facets` 与列表**同源同条件**互证 |
| 5 | 收口 mock 页可能影响既有走查脚本/用例引用 | 低 | 低 | 采用重定向（保留路径可用），并同步检索既有引用 |
| 6 | 本功能自身请求成为新日志，形成噪声 | 低 | 低 | 无需处理（符合"到达网关必留痕"口径），但**查询关键字不落日志** |
| **7** | **模块瘦身属破坏性变更**：页面迁移/删除可能打断既有深链、走查脚本、E2E 与文档引用（VC-013） | 高 | 高 | ① 迁移前产出**全量重定向映射表**，旧路径 100% 重定向不 404；② 删除/移动前**全局引用检索并存证**（路径、组件名、`AuditLogsView` 类）；③ 四模块**特色页零删减**为硬门禁；④ E2E 覆盖菜单可见性 + 深链 + 重定向 + `console.warn=0` |
| **8** | **归属判定分歧**：某页属"模块特色"还是"平台系统能力"存在主观性（如 DPS 权限/限流、LLM 工具调用监控） | 中 | 中 | ① 产出归属矩阵并**逐页给出判定理由**；② 争议页**由用户裁决**（不自行武断）；③ 判定口径写入需求（"业务特有 → 留模块；跨模块通用的治理/观测/配置能力 → 上收"） |
| **9** | **回溯返工范围失控**：需求/设计/审计文档需升版重出，若范围不清会导致反复返工 | 中 | 中 | ① VC-013 显式列明升版清单；② 本轮只回溯**前端类**设计文档，后端类（API/非功能/部署）经评估基本不受影响并登记；③ 以"归属矩阵定稿（M6）"为回溯冻结点 |
| **10** | 布局迁移期间**双入口并存**导致用户困惑 | 中 | 低 | 迁移采用"**新增即隐藏旧入口 + 保留路径重定向**"策略；迁移完成即下线旧入口，避免长期并存 |
| **11** | **模块开关管理页依赖注册表持久化形态**（若为纯配置驱动需补最小持久化）（VC-013 决议 10） | 中 | 中 | Step 2 先核实 `modules` 注册表的持久化形态；必要时**降级为只读展示**（并在需求 §4.15 登记） |
| **12** | **跨仓排期不可控（VC-014）**：R-384 需四仓各自评审与发布，**v1.4.6 收口绑定四仓节奏**；某仓延期则本版本无法收口 | **高** | **高** | ① 按 **BL-146-16（D-6 接线）/ BL-146-17（JSONL 结构化）两批**推进，批内可独立验收；② 四仓改动以《D-6 四仓 request_id 日志接线改动说明》为施工依据、各仓独立评审；③ 跨仓依赖**纳入 §3 版本依赖清单**并标注负责人与状态；④ 建议把 **G1（JSONL）与 D-6 合并同批施工**（省一轮跨仓评审/提交/回归，约 8h） |
| **13** | **生产日志量重估**：实测为 dev 强度（四仓 ≈1.82 MB/1~2 天，OpenLLM 单仓最大 1.5 MB）（VC-014） | 中 | 中 | 接入前按 QPS 重算容量；复核日志中心扫描上限（≤2 分片 / ≤200,000 行）与 `truncated` 提示是否需按新源调参 |
| **14** | **仅接线不结构化则接入价值有限**（只能关键字检索，无法按模块/结果过滤）（VC-014） | 中 | 中 | 已由 **BL-146-17（JSONL 结构化）纳入同版本**从根因消除；若拆批交付，须在批 A 交付说明中显式标注"检索能力受限" |
| **15** | 四仓日志含敏感字段（token 等）（VC-014） | 中 | 中 | BL-146-19 统一脱敏 + 沿用各仓既有脱敏逻辑 + 日志扫描单测 |
