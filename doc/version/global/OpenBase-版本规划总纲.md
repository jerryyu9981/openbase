## 1. 项目定位

OpenBase 是四系统（OpenLLM、OpenRAG、OpenMemory、DPS）及未来类似系统的**统一基础设施公共底座框架**。命名取 Open（与 AI 三件套 Open 系列一致）+ Base（底座/基础），中文名"开放底座"。

- **系列一致性**：OpenLLM → OpenRAG → OpenMemory → OpenBase（公共底座）
- **定位**：公共基础设施（鉴权/多租户/可观测/配置等），非业务系统
- **形态**：三位一体——框架内核 core + 插件模块 modules + 模板脚手架 template
- **独立维护**：独立仓库、独立版本、独立发布（PyPI）、独立文档
- **必启约束**：OpenBase 视为**必启服务**，登录与基础权限依赖 OpenBase 的 auth API；部署编排中 OpenBase 需先行启动并纳入健康检查；其余系统未启动仅隐藏对应页面，不影响登录

## 2. 两套接口体系

OpenBase 为两套接口提供统一底座（鉴权/多租户/审计/限流/可观测）：

| 接口类型 | 调用者 | 认证模型 | 性能要求 | 说明 |
|----------|--------|----------|----------|------|
| AI 服务接口 | Agent / DHAP（机器调用） | 服务级 API Key | 高并发、低延迟 | 工具注册、协议适配、MCP 封装 |
| 管理接口 | 用户（经 Vue 前端） | 用户级 JWT / RBAC | 常规 | 用户/角色/权限/租户/字典管理 |

**不可合并**：两套接口的调用者身份、认证模型、性能要求、生命周期均不同。

## 3. 前端整合方案

OpenLLM/OpenRAG/OpenMemory/DPS 四系统共用**一套统一前端**，不存在五套独立前端。前端整体基于 vue-vben-admin 构建，OpenBase 公共页面是必启基础模块，各业务系统的特色功能是统一前端中的**动态业务模块**（按服务发现动态显隐）。

> **需求设计索引**：统一前端详细需求（FR-UF-001~018 功能需求、非功能/接口/数据/权限/UI-UX 需求、追溯矩阵）见《OpenBase-统一前端需求设计说明-v0.1.0.md》（doc/requirements/）。

### 3.1 前端架构：一套统一前端 + 动态业务模块

```
┌─────────────────────────────────────────────────┐
│            统一前端（vue-vben-admin）             │
├───────────┬─────────────────────────────────────┤
│           │  工作台首页（聚合概览）               │
│  公共模块  │  系统管理（用户/角色/权限/租户…）   │ ← OpenBase 必启
│ (OpenBase) │  数据字典 / 定时任务 / 文件 / 通知   │
│           │  登录 / 鉴权                         │
├───────────┼─────────────────────────────────────┤
│           │  OpenLLM 模块（对话监控/模型/路由）  │
│ 动态模块  │  OpenRAG 模块（文档/知识库/检索）    │ ← 服务发现驱动
│ (业务域)  │  OpenMemory 模块（记忆/会话管理）    │   动态显隐
│           │  DPS 模块（画像/标签维护）           │
└───────────┴─────────────────────────────────────┘
```

### 3.2 前端实现策略：择优抽取 + 公共底座重设计

统一前端不从零新建，采用**"择优抽取 + 重设计"**策略：

| 策略 | 说明 | 适用范围 |
|------|------|---------|
| **择优抽取** | 从四系统现有前端中逐模块挑选最完整、最成熟的实现，作为统一前端对应模块的基础 | 公共模块（登录/鉴权、用户/角色/权限、租户管理等）、公共组件库、请求层、各业务域特色页面 |
| **公共底座重设计** | 整体布局、Design Token、风格体系、路由架构重新统一设计，不直接照搬任一系统，确保全新的设计质量 | 布局壳（侧边栏/顶栏/响应式）、Design Token、全局风格体系、路由架构 |
| **动态业务模块** | 各业务系统的特色功能是统一前端中的动态模块，前端代码统一维护，不分拆到各系统；按后端服务发现动态显隐 | OpenLLM 对话监控/模型管理、OpenRAG 知识库管理/检索测试、OpenMemory 记忆管理、DPS 画像管理等 |

**抽取优先级**：登录/鉴权页 → 用户/角色/权限 → 租户管理 → 公共组件 → 请求层 → 布局壳 → Design Token → 各业务域特色页面

### 3.3 模块归属划分

| 分类 | 模块 | 后端 API 提供方 | 前端来源 | 显隐方式 |
|------|------|----------------|---------|---------|
| **公共模块（OpenBase 必启）** | 登录、用户/角色/权限、租户、数据字典、定时任务、文件、通知 | OpenBase 服务 | 四系统择优抽取 + 统一设计 | 常显 |
| **动态模块 - OpenLLM 域** | 对话监控、模型管理、路由配置 | OpenLLM 服务 | 从 OpenLLM 前端择优抽取后纳入统一前端 | 服务发现驱动 |
| **动态模块 - OpenRAG 域** | 文档管理、知识库配置、检索测试 | OpenRAG 服务 | 从 OpenRAG 前端择优抽取后纳入统一前端 | 服务发现驱动 |
| **动态模块 - OpenMemory 域** | 记忆管理、会话管理 | OpenMemory 服务 | 从 OpenMemory 前端择优抽取后纳入统一前端 | 服务发现驱动 |
| **动态模块 - DPS 域** | 画像管理、标签维护 | DPS 服务 | 从 DPS 前端择优抽取后纳入统一前端 | 服务发现驱动 |

### 3.4 布局与主题

- **菜单分组**："系统管理"分组（OpenBase 公共模块，常显）+ 各业务域分组（动态，服务发现驱动）
- **工作台首页**：聚合工作台（各在线业务模块状态概览卡片，未启动的模块显示"未启动"）
- **公共模块常显**：OpenBase 公共模块菜单不随服务发现隐藏；各业务域模块随服务状态动态显示
- **Design Token**：基于四系统现有主题重新设计全站统一 Design Token，所有模块统一使用
- **公共组件**：从四系统中挑选成熟度最高的表格/表单/弹窗/图表组件，统一封装为公共组件库，所有模块直接引用

### 3.5 共用/独立双模式

| 模式 | 场景 | 前端包含内容 |
|------|------|-------------|
| **共用模式（默认）** | 四系统整体部署 | 统一前端 = 公共模块（OpenBase） + 全部业务域动态模块（OpenLLM/OpenRAG/OpenMemory/DPS） |
| **独立模式** | 单系统单独部署 | 统一前端 = 公共模块（OpenBase） + 对应业务域动态模块（如仅 OpenLLM 模块） |

> 双模式通过构建配置控制，前端代码库是同一套，仅按需加载对应业务域模块。

## 4. 项目长期目标

1. **消除重复开发**：四系统公共能力（6 核心模块 + 补齐模块）单一事实源
2. **最小改动接入**：从现有系统抽取最成熟实现，四系统以插件方式挂载，特色功能不动
3. **可插拔复用**：新系统一条命令初始化即获得全部公共能力
4. **独立演进**：底座独立版本管理与发布，不影响各系统特色迭代

## 5. 版本节奏与命名

### 5.1 版本命名规则

采用语义化版本（主.次.修订）：
- **主版本**：重大架构变更、不兼容升级
- **次版本**：新增功能模块、里程碑发布
- **修订号**：Bug 修复、纠错

### 5.2 版本节奏

| 版本类型 | 节奏 | 说明 |
|----------|------|------|
| 主版本 (x.0.0) | 按里程碑 | 架构稳定后发布，不频繁 |
| 次版本 (x.y.0) | 2-4 周 | 新模块/新能力迭代 |
| 修订版本 (x.y.z) | 按需 | Bug 修复、热补丁 |

### 5.3 内核与模块版本

- **内核（core）**：API 稳定，非必要不变化；变更需评审
- **模块（modules）**：各模块独立小版本，可独立升级
- **CHANGELOG.md** 同步记录所有变更

## 6. 治理原则

1. **单一事实源**：公共能力唯一实现在 OpenBase 中
2. **保留最完整实现**：模块级择优抽取，不从零开发
3. **三不原则**：不删除原实现（Git 历史保留）、不急于替换（灰度迁移）、不回退特色
4. **配置驱动启用**：弱依赖、可插拔，模块独立启用/禁用
5. **内核最小化**：避免过度设计，插件独立演进

## 7. 兼容策略

- Python 3.11+ 保持兼容
- FastAPI 当前稳定版本
- 内核 API 向后兼容，破坏性变更需主版本升级
- 模块间弱依赖，单模块故障不拖垮整体
- 配置变更可回滚
- 底座化不影响各系统对外接口（AI 服务接口与 MCP 工具清单不变）

## 8. 发布策略概述

- **CI/CD**：单元测试 + 静态检查（ruff）+ 覆盖率门槛（≥85%）+ 自动发布
- **PyPI 发布**：`pip install openbase`
- **灰度策略**：按"低风险模块先行"（audit/otel）→ 高风险模块（鉴权/多租户）顺序灰度切换
- **灰度切换三阶段**：Dev（替换 audit/otel）→ Test（替换 auth/tenant/config/mcp）→ Pro（全量切换）
- **回滚策略**：失败可 git revert，模块级回滚不影响其他模块
