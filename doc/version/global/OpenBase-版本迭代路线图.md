## 1. 路线图概览

```
v1.0.0 ─────→ v1.1.0 ─────→ v1.2.0 ─────→ v1.3.0 ─────→ v1.4.0
首个可用底座   四系统接入     统一前端      功能补全+对接   完备+生态
S0审计+S1抽取  S3回灌        统一前端     P0 26+P1 4项     P1/P2 全量
S2补齐+S4发布  +AI规则适配   底座+占位页   四系统API对接    生态工具链
6-7周         4-5周         5-6周        14周            12-14周
```

> 版本规划调整（2026-08-25，VC-001）：废除原 v0.1.0 独立版本（审计+抽取并入 v1.0.0），版本收敛为 3 个近期发布版本 + 1 个远期，每版本主题聚焦、工作量充足、独立闭环。详见《OpenBase-版本范围变更总记录》。
>
> 版本规划合并（2026-08-27，VC-003）：基于《OpenBase-统一前端与独立前端功能差距分析-v1.2.0.md》§10 建议（原 v1.2.1/v1.3.0/v1.4.0/v1.5.0 四版本），合并为 v1.3.0（P0 必须保留 26 项：先补全、再对接）+ v1.4.0（P1 建议保留项 + 生态工具链）两版本。原 v1.3+ 生态项并入 v1.4.0。详见《OpenBase-版本范围变更总记录》。
>
> 版本范围扩展（2026-08-27，VC-004）：用户业务输入"P0 必须补齐，P1、P2 等也都需要补齐"。科学分配：v1.3.0 扩至 P0 26 + 高耦合 P1 4（约 30 项，14 周）；v1.4.0 从远期转为明确排期（剩余 P1 + P2 + 生态全量，约 12-14 周）；版本数量维持 2 个。
>
> 交付策略调整（2026-08-27，VC-005）：用户业务输入"前端完整后，除基座部分功能属于本次必须与后台调试完整外，OpenMemory/OpenRAG/OpenLLM/DPS 部分与后台接口对接调试暂时挂起，后续根据需要一部分一部分地与后端 API 调试"。v1.3.0 调整为"前端完整 + 基座调试完整 + 四系统对接挂起分批"。
>
> 版本范围扩展（2026-08-28，VC-006）：统一网关（服务发现/路由转发/聚合）与 API 服务框架归属确认均属 OpenBase；网关增强（R-365 后端实例服务发现 + R-366 聚合编排）按《网关服务发现与聚合编排技术方案》（ADR-网关-001/002）纳入 v1.4.0，阶段一零依赖落地（config+scheduler 探测 + 代码式聚合），阶段二（Nacos/DSL/GraphQL）需求驱动再排期；网关并行排期 6 周，不改变 v1.4.0 总周期。详见《OpenBase-版本范围变更总记录》。
>
> 生态工具链挂起（2026-08-28，VC-007）：用户决策"生态工具链先挂起，其他继续"——i18n/测试基座/文档站点/示例项目（R-364）从 v1.4.0 范围移出，返回候选需求池待后续版本排期；v1.4.0 保留 P1 补齐 + P2 保留 + 统一网关增强，周期不变。详见《OpenBase-版本范围变更总记录》。
>
> 后续版本对接策略调整（2026-08-30，VC-011）：用户决策"OpenBase 的后续版本规划先暂时小版本一个一个对接，完成初步测试之后，再进行所有的统一集成测试"；并明确"对接从 v1.4.3 开始"，"四系统统一集成测试 + 平台治理（收官）移到 v1.5"。原 v1.5 一次性大版本（平台治理与协同集成）拆分为 1.4.x 连续小版本逐个系统对接线：v1.4.3 OpenLLM 对接 → v1.4.4 OpenRAG 对接 → v1.4.5 DPS 对接 → v1.5 四系统统一集成测试 + 平台治理（收官）。每个小版本独立完成对接 + 初步测试闭环；统一集成测试集中到 v1.5。详见《OpenBase-版本范围变更总记录》。
