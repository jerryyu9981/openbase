## 2. 灰度策略

### 2.1 模块级灰度

按"低风险模块先行"原则：

| 灰度顺序 | 模块 | 风险等级 | 说明 |
|----------|------|----------|------|
| 第一批 | audit / observability | 低 | 只读辅助，不影响核心逻辑 |
| 第二批 | config | 低 | 配置管理，可回滚 |
| 第三批 | mcp | 中 | 工具协议，接口影响可控 |
| 第四批 | auth (RBAC) | 高 | 鉴权核心，需充分测试 |
| 第五批 | tenant | 高 | 多租户隔离，数据安全相关 |

### 2.2 系统级灰度

1. 单系统接入验证（OpenLLM 优先，基座系统）
2. 逐步扩展至其他系统（OpenRAG → OpenMemory → DPS）
3. 每系统灰度验证通过后方可收敛

### 2.3 灰度切换三阶段验证

> 来源：OpenLLM 方案 §1.10.4（v1.4.4）

每系统接入 OpenBase 时，按以下三阶段灰度切换：

| 阶段 | 环境 | 替换内容 | 验证标准 |
|------|------|----------|----------|
| Dev | 开发环境 | 先替换 audit / otel（低风险模块） | 单测 + 集成测试通过 |
| Test | 测试环境 | 替换鉴权 / 多租户 / 配置 / MCP，数据同步 | E2E + 多租户回归 |
| Pro | 生产环境 | 全量切换，旧实现冻结（Git 历史保留） | 上线检查 + 监控 |

**回滚预案**：任一阶段验证失败则 `git revert`（旧实现完整保留于 Git 历史）。底座化不影响各系统对外接口（AI 服务接口与 MCP 工具清单不变）。

**回灌顺序**：OpenLLM → OpenRAG → OpenMemory → DPS（逐系统灰度）

## 3. 回滚原则

- **模块级回滚**：单模块故障可独立禁用（`settings.disable_module`），不影响其他模块
- **版本级回滚**：`pip install openbase=={上一个稳定版本}`
- **Git 回滚**：`git revert` 回退代码变更，Git 历史保留
- **配置回滚**：配置中心支持版本回滚（三级配置合并 + 版本管理）

## 4. 兼容策略

| 维度 | 策略 |
|------|------|
| Python 版本 | 3.11+ 保持兼容 |
| FastAPI | 当前稳定版本 |
| 内核 API | 向后兼容，破坏性变更需主版本升级 |
| 模块间 | 弱依赖，单模块禁用不影响其他 |
| 数据库 | Alembic 迁移脚本保证可回滚 |

## 7. 部署编排约束

> 来源：OpenLLM 方案 §15.7（v1.4.5）

### 7.1 OpenBase 必启约束

登录与基础权限依赖 OpenBase 服务的 auth API，因此 **OpenBase 视为必启服务**。部署编排中 OpenBase 需先行启动并纳入健康检查；其余业务服务未启动仅隐藏统一前端中的对应动态模块，不影响登录和公共模块使用。

| 约束 | 说明 |
|------|------|
| 启动顺序 | OpenBase → 其余业务服务（OpenLLM/OpenRAG/OpenMemory/DPS） |
| 健康检查 | OpenBase 必须通过 /health 检查后方可启动其他服务 |
| 前端影响 | 统一前端中 OpenBase 公共模块常显（登录/用户/角色/权限/租户等），不随服务发现隐藏 |
| 降级行为 | OpenBase 不可用时，登录功能不可用；统一前端其余页面（如已登录）仍可访问 |

### 7.2 共用 / 独立双模式

统一前端为**一套代码库**，双模式通过构建配置控制业务域模块加载。

| 模式 | 场景 | 前端包含内容 |
|------|------|-------------|
| **共用模式（默认）** | 四系统整体部署 | 统一前端 = 公共模块（OpenBase） + 全部业务域动态模块（OpenLLM/OpenRAG/OpenMemory/DPS） |
| **独立模式** | 单系统单独部署 | 统一前端 = 公共模块（OpenBase） + 对应业务域动态模块（如仅 OpenLLM 模块） |

### 7.3 服务发现动态模块

- 各业务域动态模块（OpenLLM 对话监控、OpenRAG 知识库管理、OpenMemory 记忆管理、DPS 画像管理等）按后端服务发现动态显隐
- 后端服务未启动时，对应业务域菜单与路由自动隐藏
- 服务恢复后自动出现（30s 轮询或 SSE/WebSocket 推送）
- OpenBase 公共模块不随服务发现隐藏（常显）

## 8. 组件化集成发布策略

> 来源：OpenLLM 方案 §2.4（v1.4.5）+ 复用框架研究报告 §5

OpenBase 内部采用成熟开源组件，按优先级分批集成：

| 批次 | 组件 | 优先级 | 形态 | 集成版本 |
|------|------|--------|------|----------|
| 第一批 | FastMCP、Langfuse、OpenTelemetry | P0 | 进程内库/独立服务 | v1.0.0（首个可用底座集成） |
| 第二批 | Qdrant、GPTCache | P1 | 独立服务/进程内库 | v1.0.0（首个可用底座集成） |
| 第三批 | Mem0、LlamaIndex | P2 可选 | 进程内库 | v1.3+（按需引入） |

**集成原则**：
- 组件全部封装于模块内部，对外接口保持不变
- 遵循"直接采用 / 封装采用 / 自研保留"三级复用策略
- 组件升级或替换不影响上层调用方
- License 优先 MIT/Apache 2.0，避免 AGPL 传染性
